## 缓存

缓存就是把一次昂贵操作的结果存下来，下次再要的时候直接给出去，不必重做一遍。这里的「昂贵操作」通常指数据库查询、外部 API 调用，或者一段重计算。

它最根本的权衡是新鲜度对速度。缓存永远只是真相的一份副本，而不是真相本身。数据一旦被缓存，就开始变陈旧。你要做的判断是：对某一类数据来说，多大程度的陈旧是可以接受的。

**缓存放在哪里：**

进程内缓存把数据放在应用自己的内存里。这是最快的方案，因为没有网络往返。代价是每个应用实例都有自己的一份缓存，所以在水平扩展的系统里，各实例之间会不一致。适合很少变动的数据，比如功能开关或配置项。

分布式缓存（Redis、Memcached）作为一个共享服务运行在应用之外。所有实例访问同一份缓存，因此能保持一致。多了一次网络往返，但仍然比数据库查询快好几个数量级。这是大多数生产系统的标准选择。

CDN 缓存位于网络边缘节点，负责静态资源和可缓存的 HTTP 响应。它不直接归你的应用管，但作为整幅图景的一部分值得了解。

**缓存失效**才是难的地方。有句名言说，缓存失效和命名是计算机科学中最难的两个问题。常见策略有：

**TTL（存活时间）：** 缓存条目在设定时长后过期。实现简单，但你得接受在 TTL 窗口内会返回陈旧数据。

**写穿透（Write-through）：** 更新数据库的同时，立刻更新或删除对应的缓存条目。缓存更新鲜，但每条写路径都变复杂了。

**事件驱动失效：** 数据变化时由某处发布一个事件，订阅者删掉相关的缓存键。这是规模化之后最干净的做法，但需要有事件基础设施。

**旁路缓存（Cache-aside）** 是最常见的模式。应用先查缓存：命中就返回缓存值；未命中就去数据库取，把结果写进缓存，再返回。简单、直白，而且由应用自己控制缓存什么、什么时候缓存。

有几件事经常把人坑到：缓存频繁变动的数据；把用户专属的数据缓存在共享键上（导致数据跨用户泄露）；不缓存错误（大量请求同时未命中，一起冲垮数据库，也就是惊群效应）；以及忘了处理缓存为空的冷启动情况。

## 任务队列

有些工作不该发生在请求-响应周期里。发邮件、给上传的图片压缩尺寸、生成 PDF、把数据同步到第三方 API——这些用户都没必要等。任务队列能把这类工作从 HTTP 处理函数里挪出来，异步执行。

模型很简单：一个**生产者**把作业放进队列，一个或多个**工作进程**从队列里取出作业并执行。HTTP 请求在入队之后立即返回，用户看到了响应，重活在后台进行。

POST /upload-video -\> 保存原始文件 -\> 入队作业 { type: "transcode", fileId: "abc123" } -\> 返回 202 Accepted（不是 200 —— 活儿还没干完）工作进程稍后取走这个作业： -\> 转码文件 -\> 更新数据库 -\> 给用户发通知

常见的队列系统：基于 Redis 的队列（Node.js 里的 BullMQ、Python 里搭配 Redis 的 Celery）、RabbitMQ、Amazon SQS，如果你还需要它同时充当事件流，那就用 Kafka。

**重试与幂等性**没有商量余地。工作进程会挂，网络会断。你的作业必须能安全地跑不止一次。如果一个转码作业跑了两遍，你最终应该得到一个转码后的文件，而不是两个。在你开始考虑重试逻辑之前，先把作业设计成幂等的。

**死信队列**用来存放失败次数超过重试上限的作业。与其悄无声息地丢掉一个失败作业，不如把它停在一个你能检查的地方，修完 bug 后手动重新处理。设计队列系统时，绝不要不带死信队列。

**并发与背压**在规模上来后很关键。假如你有十个工作进程，同时涌进来一百万个作业，那么工作进程的取件速率必须是下游系统（数据库、第三方 API）扛得住的。要有意识地限制工作进程的并发度。

作业的可见性是团队普遍低估的一件事。「这个作业干完了没有？」是用户一定会问的问题。如果这关系到用户体验，就做一套追踪作业状态的机制。

## 错误处理

后端系统里的错误大致分两类：**运行性错误**和**程序员错误**。

运行性错误是预料之中的，属于系统正常运转的一部分：用户传了非法输入、数据库里没找到某条记录、第三方 API 超时、支付被拒。这些不是 bug，而是你事先预见并要优雅处理的情况。

程序员错误是 bug：空引用、未被捕获的 promise rejection、越界访问。这些不该在运行时去「处理」，它们应该大声地崩掉、立刻被记录下来，然后被修掉。

一个常见错误是把所有错误一视同仁。如果你捕获所有异常并统一返回 500，你既掩盖了那些本该返回 404 或 422 的运行性错误，也把真正的 bug 藏在了同一个笼统的响应之下。两类问题都更难排查了。

**类型化 / 自定义错误类**是给运行性错误建模最干净的方式：

```javascript
class NotFoundError extends AppError {
  statusCode = 404;
  constructor(resource) {
    super(\`${resource} not found\`);
  }
}

class ValidationError extends AppError {
  statusCode = 422;
  constructor(violations) {
    super("Validation failed");
    this.violations = violations;
  }
}
```

全局错误处理器捕获这些类型化的错误，映射成正确的 HTTP 响应。任何不属于已知 AppError 子类的东西，都按未预期的 bug 对待，返回 500。

**统一的错误响应结构**对 API 使用方很重要：

```javascript
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Validation failed",
    "violations": [
      { "field": "email", "message": "must be a valid email address" }
    ]
  }
}
```

选定一种结构，然后处处坚持它。如果你一半的接口端点返回 { "error": "..." }，另一半返回 { "message": "..." }，客户端开发者会恨死你的 API。

**异步代码里的错误传播**需要纪律。在 Node.js 中，未处理的 promise rejection 曾经会静默吞掉错误。要么老老实实地 await，要么串上 .catch()。在有受检异常的语言里，不要为了让编译器闭嘴而压掉异常。

还有一点：在生产环境中不要把堆栈信息或内部错误细节暴露给客户端。完整错误在内部记录，对外只发一条干净、安全的消息。

## **日志**

日志是你理解系统究竟做了什么的首要工具——不是你以为它做了什么，而是它实际做了什么。

**日志级别**的存在是有道理的，请用起来：

- DEBUG：细粒度的细节，开发时有用，生产环境里太吵
- INFO：值得记录的正常操作（用户已创建、作业已完成、服务已启动）
- WARN：发生了预期之外但可恢复的事
- ERROR：某处失败了，需要关注
- FATAL：应用无法继续，正在关闭

在生产环境跑 DEBUG 级别会撑爆日志存储，反而让真正的问题更难被找到。用 INFO 或 WARN。

**结构化日志**在生产系统里没有商量余地。记录 JSON，不要记录纯文本字符串。

**差的写法：**

\[2024-01-15 10:30:00\] User 123 placed order 456 for $99.00

**好的写法：**

```json
{
  "timestamp": "2024-01-15T10:30:00Z",
  "level": "info",
  "event": "order_placed",
  "userId": 123,
  "orderId": 456,
  "amount": 9900,
  "requestId": "req_7f3a9b"
}
```

第二种格式是可查询的。你可以按 userId 过滤、按 event 聚合、用 requestId 把不同服务的日志关联起来。第一种格式只是一串字符串，你得用正则去解析，还得祈祷格式永远不变。

**关联 ID / 请求 ID** 把同一次请求产生的所有日志串成一条可追溯的线索。在边缘处（中间件里）生成一个唯一 ID，挂到请求上下文上，并让这次请求期间输出的每一行日志都带上它。当用户报 bug 时，你拿着他们的请求 ID，就能把这次请求在各个服务里留下的每一行日志都捞出来。

该记什么：生命周期事件（请求已接收、请求已完成）、系统做出的决策（记「支付被拒，因为余额不足」，而不只是「支付失败」）、外部调用及其结果，以及带完整上下文的错误。

不该记什么：密码、token、信用卡号、你并不需要的个人身份信息。记用户 ID，别记用户完整档案。记「认证失败」，别记尝试过的那个密码。

## 监控

日志告诉你发生了什么，监控告诉你系统此刻、以及一段时间以来表现如何，一眼就能看到。

**可观测性的三大支柱**是日志、指标和链路追踪。日志你已经知道了。指标是随时间变化的数值测量。链路追踪则跟随一次请求穿过多个服务的全过程。

**指标**是仪表盘的构成基础。每个后端服务都该追踪的四个信号：

- **延迟**：请求完成需要多久（要看 p50、p95、p99，不能只看平均值）
- **流量**：每秒请求数
- **错误率**：出错请求所占的百分比
- **饱和度**：资源用得有多满（CPU、内存、队列积压深度、数据库连接数）

它们被称为**四个黄金信号**，出自 Google 的 SRE 手册。如果这四项都健康，你的服务基本可以确定没问题；只要其中任何一项劣化，你就有了排查的起点。

**告警**是大多数团队一开始都会做砸的部分。要对症状告警，而不是对原因告警。「错误率连续 2 分钟高于 5%」是症状——此刻用户那边确实有东西坏了。「CPU 高于 80%」是原因，也许有意义，也许没有。对每一种可能的原因都告警，只会导致告警疲劳：告警多到人人都视而不见。

**分布式追踪**（Jaeger、Zipkin、Honeycomb、Datadog APM）让你能跟着一次请求穿过多个服务，看清时间到底花在哪儿了。当一次请求耗时 2 秒、涉及五个服务时，一条 trace 会告诉你其中 1.8 秒被哪个服务吃掉了。没有追踪，你只能靠猜。

**健康检查端点**简单但重要。一个 /health 路由，在服务存活、能连上数据库、能连上关键依赖时返回 200。负载均衡器和编排系统（Kubernetes）靠它来决定要不要把流量发给某个实例。

## 优雅关闭

当你的应用进程收到终止信号（类 Unix 系统里的 SIGTERM）时，它能做的最糟糕的事就是立刻死掉。正在处理中的请求会被丢弃，执行到一半的作业被抛下、把数据留在残缺状态，数据库连接没清理就被切断。

优雅关闭就是捕获这个信号，收拾干净之后再退出。

流程大致是这样：

1\. 收到 SIGTERM 2. 停止接受新请求（关闭 HTTP 服务器对新连接的监听） 3. 等待处理中的请求完成 4. 完成或对进行中的后台作业做检查点 5. 关闭数据库连接和其他资源 6. 以状态码 0 退出

```javascript
process.on('SIGTERM', async () => {
  console.log('Shutting down gracefully...');

  server.close(async () => {
    await jobQueue.close();
    await db.disconnect();
    process.exit(0);
  });
});
```

**超时**是安全阀。你不能无限期地等请求跑完。设一个截止时间，视工作负载而定通常是 10 到 30 秒，超时之后强制退出。一个卡死的请求不该无限期地拖住你的部署。

这一点在容器化环境里尤其重要。Kubernetes 在杀掉 pod 之前会先发 SIGTERM。如果你的应用不处理它，Kubernetes 会等满 terminationGracePeriodSeconds（默认 30 秒），然后发 SIGKILL，那是立即的硬杀。如果你的优雅关闭在这个截止时间之前完成，用户根本察觉不到 pod 被替换过；如果没完成，你就是在丢请求。

对任务队列的工作进程来说，优雅关闭意味着先干完当前作业再停下，而不是中途抛下它、让它平白无故消耗一次重试计数。作为关闭流程的一部分，要显式地确认（ack）或重新入队当前作业。

这六件事并不是彼此独立的，它们时刻都在相互作用：

一个请求进来，**中间件**注入请求 ID。处理函数先查**缓存**，未命中就查数据库并把结果存起来。它为某个副作用入队了一个后台**任务**。一旦哪里出了问题，**错误处理**接住它，**日志**带着请求 ID 记录下来，**监控**捕捉到错误率往上跳。等到发布上线时，**优雅关闭**确保响应先发完，进程再退出。

这些都不是什么「特性」，它们是生产级后端的基本盘。从一开始就把它们建进去，而不是事后补。
