## 安全

```javascript
// This blocks the event loop for every other request while it runs
app.get('/compute', (req, res) => {
  const result = heavyCpuComputation(); // bad on the main thread
  res.json({ result });
});
```

安全不是最后加上去的一项功能，而是从一开始就要建进系统每一层的一种属性。目标不是让系统坚不可摧（没有东西是坚不可摧的），而是让攻击的代价高到攻击者转身走人。

**认证 vs 授权**

这两个概念老是被搞混。认证回答的是「你是谁？」，授权回答的是「你被允许做什么？」。它们是两件不同的事，应该待在不同的层里。

认证通常发生在中间件这一层：校验一个 JWT、验证一个会话、查一把 API key。认证失败就返回 401（Unauthorized，这个词有点误导，它其实是「未认证」）。

授权则更靠近资源。在你知道用户是谁之后，再检查他有没有执行所请求操作的权限。如果已认证但没权限，返回 403（Forbidden）。

一个常见错误是把两者混为一谈：把权限检查塞进认证中间件里，用一道关卡想同时搞定两件事。让它们保持分离。认证告诉你是谁在发这个请求，授权告诉你他能拿这个请求做什么。

**JWT 与会话**

JWT 是无状态的 token。服务端签发一个带签名的 token，里面装着声明（用户 ID、角色、过期时间）。后续请求中客户端把 token 带回来，服务端验证签名，然后不查数据库就信任这些声明。快、无状态、易于水平扩展。

代价是：JWT 在过期之前无法撤销。如果一个用户登出或者被封号，他的 token 在过期前依然有效。解法包括把有效期设得很短（15 分钟）并配合刷新 token，或者在 Redis 里维护一份小小的撤销名单。

会话是有状态的。服务端把会话数据存起来（内存、Redis 或数据库），通过 cookie 给客户端一个不透明的会话 ID。每次请求，服务端都去查这个会话。这样能做到即时撤销，但在扩展后的环境里需要共享的会话存储。

两者没有绝对的优劣。JWT 适合无状态 API 和移动端；会话适合传统 Web 应用——那里客户端在你自己的掌控之下。

**密码存储**

绝不要明文存储密码。也绝不要存成 MD5 或 SHA-256 哈希。那些是快速哈希算法，而「快」恰恰是密码最不该有的属性。拿到你数据库的攻击者，每秒能对 SHA-256 哈希跑上十亿次猜测。

用 bcrypt、scrypt 或 Argon2。它们被有意设计得又慢又吃内存，还会自动加盐，也就是说两个相同的密码会产生不同的哈希。Argon2 是当前大多数安全权威机构推荐的选择。

```javascript
const hash = await bcrypt.hash(password, 12); // cost factor of 12
const valid = await bcrypt.compare(inputPassword, hash);
```

代价因子（cost factor）控制哈希有多慢。数值越高越安全，也越慢。10 到 12 是个合理的默认值。

**常见漏洞**

**SQL 注入**：攻击者把 SQL 注入到用户输入里，从而操纵你的查询。修复办法永远是参数化查询或预编译语句。绝不要把用户输入拼接进 SQL 字符串。

```javascript
// Vulnerable
db.query(\`SELECT * FROM users WHERE email = '${email}'\`);

// Safe
db.query(\`SELECT * FROM users WHERE email = $1\`, [email]);
```

**XSS（跨站脚本）**：攻击者把 JavaScript 注入到你的响应中，然后在其他用户的浏览器里执行。要对输出做净化处理，使用 Content-Security-Policy 响应头，并避免用不可信数据去设置 innerHTML。

**CSRF（跨站请求伪造）**：攻击者诱使用户的浏览器从一个恶意站点向你的 API 发出一个已认证的请求。对基于会话的应用用 CSRF token 来缓解，或者依靠 CORS 和 SameSite cookie。

**IDOR（不安全的直接对象引用）**：一个用户请求 /orders/1234，拿回了属于另一个用户的订单，因为你只检查了认证、没检查授权。永远要验证已认证的用户确实有权访问他所请求的那个具体资源，而不只是验证他登录了。

**限流与暴力破解防护**：登录端点、密码重置端点、OTP 验证端点都需要限流。一个没有防护的登录端点可以被无限制地暴力破解。要用指数退避，并在反复失败后锁定账号。

**密钥管理**

绝不要把密钥放进代码里。API key 不行，数据库密码不行，JWT 签名密钥也不行。哪怕是放在一个会被提交进仓库的 .env 文件里，也不行。

用运行时注入的环境变量，或者一套正经的密钥管理服务（AWS Secrets Manager、HashiCorp Vault、GCP Secret Manager）。定期轮换密钥，审计谁有访问权限。一旦密钥泄露，就当作凭据已被攻破处理——立刻轮换。

**传输安全**

处处使用 HTTPS。TLS 加密传输中的数据，让网络上的窥探者既读不到也改不了。要强制执行：把 HTTP 重定向到 HTTPS，设置 Strict-Transport-Security 响应头，绝不通过明文 HTTP 发送敏感数据。

向外部服务发起请求时，要校验 TLS 证书。为了「修好」一个连接错误而跳过证书校验，等于拿一个网络 bug 换来了一个安全漏洞。

## 扩展与性能

扩展说的是让系统扛住更多负载，性能说的是让系统用现有的资源做更多事。两者相关但不同。最好的扩展策略，是先把现有资源的性能榨出来，从而少扩一点。

**垂直扩展 vs 水平扩展**

垂直扩展就是给服务器更多资源：更多 CPU、更多内存、更快的磁盘。它简单，不需要改应用。但它有一个硬天花板：单台机器只能强到那个程度，过了某个点成本就贵得离谱。

水平扩展是增加应用实例数量，把负载分散到它们身上。它实际上没有上限，而且现代云基础设施就是为这个模型建的。代价是应用必须为此而设计：不要本地状态，会话要外置，缓存要分布式，等等。

多数系统一开始是垂直扩展，随着增长转向水平扩展。哪怕你现在还不需要，也要从一开始就按水平扩展来设计。养成这些习惯的成本很低，日后重构的成本可不低。

**负载均衡**

负载均衡器坐在你的应用实例前面，分发进来的请求。常见策略有轮询（每个实例轮流接收请求）、最少连接（活跃连接最少的实例接下一个请求），以及 IP 哈希（同一个客户端 IP 总是路由到同一个实例，在需要会话粘性时有用）。

你的应用实例应当是无状态的，这样任何实例都能处理任何请求。如果实例 A 有本地状态而实例 B 没有，路由决策会变得复杂，故障也会变得难受。

**数据库性能**

数据库几乎总是最先成为瓶颈的那个。应用服务器无状态，很容易水平扩展；数据库带着状态，扩起来难得多。

**索引**是数据库性能收益的主要来源。一条要扫一百万行的查询，加上合适的索引后可能只扫几行。理解你的查询模式，给用来过滤和排序的列加索引。但也别索引过头：每个索引都会拖慢写入并占用存储。

**N+1 查询**是无声的杀手。你取回一个 100 个用户的列表，然后遍历它，为每个用户单独发一条查询取他的订单。本来 2 条查询能搞定的事，变成了 101 条。用预加载（JOIN 或 ORM 的 include）在一次往返里把关联数据一起取回来。

**连接池**避免应用在每个请求上都新建一条数据库连接。建立连接的开销很大。连接池维护一组已打开的连接，按需借给请求使用。PostgreSQL 可以用 PgBouncer，或者用你的 ORM 自带的连接池配置。

**读副本**让你能把读流量分散开。大多数应用读远多于写。主节点处理写，一个或多个副本处理读。复制延迟是一个实实在在的问题：写在主节点上落地之后，副本上未必立刻可见。你要清楚哪些读需要强一致性（走主节点），哪些能容忍轻微延迟（走副本）。

**分页**在规模上来之后不是可选项。把一张表的全部记录返回给客户端是性能灾难。用基于游标的分页（更高效）或基于偏移量的分页（更简单），并强制设定合理的页大小上限。

**用缓存换性能**

这一节接回缓存那部分：能缓存的就大胆缓存。一次缓存命中意味着没有数据库查询、没有计算，只有一次内存读取。在高负载下，从缓存返回响应和从数据库返回响应之间的差别，往往就是系统撑住和系统垮掉之间的差别。

**性能剖析与定位瓶颈**

不要靠猜来判断性能问题出在哪儿。先做剖析。Node.js 里用内置 profiler 或 clinic.js；Python 里用 cProfile 或 py-spy；Java 里用 async-profiler 或 JFR。

要关注：慢查询（用数据库的慢查询日志）、过量的内存分配、阻塞事件循环的 CPU 密集型工作，以及不必要的序列化和反序列化。

一个常见陷阱是优化错了对象。花一周时间给一个每小时才跑一次的函数省下 10 毫秒，而每个请求上都挂着一条 200 毫秒的数据库查询——这笔买卖很亏。先剖析，找到真正的热点，去修它。

**面向性能的 API 设计**

保持响应负载数据精简。客户端只需要 5 个字段时，不要返回 50 个。如果过度取数是个长期存在的问题，可以考虑字段选择（让客户端指定要哪些字段）或者上 GraphQL。

用 gzip 或 Brotli 压缩响应。一个 500KB 的 JSON 负载压到 50KB，意味着更少的带宽和更快的传输时间，在移动端尤其明显。

也要为客户端缓存做设计。使用 ETag 和 Cache-Control 响应头，这样当客户端的缓存版本仍然新鲜时，它可以干脆跳过这次请求。

## 并发与并行

这两个词经常被混用，但含义不同。并发讲的是同时应付多件事，并行讲的是同时做多件事。你可以有并发而没有并行。

一个跑着事件循环的单核 CPU 是并发的：它在任务之间快速切换，让多件事都有进展。但它不是并行的：任一瞬间只有一件事在执行。两个 CPU 核心同时处理两个任务，那才是并行。

**事件循环模型（Node.js）**

Node.js 跑在单线程上，带一个事件循环。它通过非阻塞 I/O 来实现并发。当你的代码发起一次数据库查询时，它不会坐在那儿干等，而是注册一个回调，把控制权交还给事件循环，事件循环转去处理下一个待办任务。等数据库响应回来，那个回调再执行。

这个模型对 I/O 密集型的工作（Web 服务器、API 网关，以及任何在等数据库或网络的场景）效率极高。但它不适合 CPU 密集型的工作：一次重计算就会阻塞整个事件循环，让其他所有请求都卡住。

```javascript
// This blocks the event loop for every other request while it runs
app.get('/compute', (req, res) => {
  const result = heavyCpuComputation(); // bad on the main thread
  res.json({ result });
});
```

Node.js 里的 CPU 密集型工作，要卸载到 Worker Threads 或者独立进程中去。不要阻塞事件循环。

**线程模型（Java、Go、Python）**

Java 用的是操作系统线程。每个请求从线程池里拿一个线程。线程在多核 CPU 上能真正并行运行。代价是内存（每个线程都有自己的栈，通常 1MB 起）和上下文切换开销。线程池的大小必须仔细斟酌：太小则请求排队，太大则耗尽内存。

Go 用的是 goroutine，一种由 Go 运行时管理的轻量级绿色线程。你可以跑上百万个 goroutine，而不必承担操作系统线程的内存开销。Go 调度器把 goroutine 映射到操作系统线程上，多路复用的事情它替你办了。在 Go 里，并发既地道又廉价。

Python 有全局解释器锁（GIL），它阻止多个线程真正并行地执行 Python 字节码。Python 线程能为 I/O 密集型工作提供并发，但无法为 CPU 密集型工作提供并行。要在 Python 里实现 CPU 密集型的并行，用 multiprocessing 模块，它会派生出各自拥有独立 GIL 的多个进程。

**竞态条件**

竞态条件发生在两个并发操作都对共享状态做读写、而最终结果取决于执行顺序的时候。经典例子：

线程 A 读取余额：100 线程 B 读取余额：100 线程 A 写入余额：100 - 50 = 50 线程 B 写入余额：100 - 50 = 50 // 错了，应该是 0

两个线程都在对方写入之前完成了读取。最终余额是 50，而它本该是 0——凭空多出了五十块钱。

修复手段包括：数据库层面的加锁（SELECT FOR UPDATE）、乐观锁（在更新语句里带上版本号，不匹配就失败），或者原子操作（用数据库事务把「读-改-写」变成一个不可分割的整体）。

在代码层面，互斥锁（mutex）通过保证同一时刻只有一个线程能访问共享状态来保护它。要克制着用。锁持有太久会造成争用，实际上把并发的工作串行化了，也就违背了并发的初衷。

**死锁**

死锁发生在两个操作各自等着对方持有的资源，谁都动不了的时候。

事务 A 锁住第 1 行，等待第 2 行 事务 B 锁住第 2 行，等待第 1 行 两者永远等下去

预防策略：所有操作都按一致的顺序获取锁；事务保持简短，尽快释放锁；获取锁时使用超时，而不是无限期等待。

大多数数据库能检测到死锁，并自动回滚其中一个事务。那个事务会走到你的错误处理代码里。重试它就好。

**Async/Await 与结构化并发**

Async/await 是 promise 或 future 之上的语法糖。它让异步代码看起来像同步代码，比嵌套回调或裸的 promise 链条好推理得多。

一个常见的性能失误，是把本可以并行跑的工作串行化了：

```javascript
// Sequential: takes 300ms total (100 + 100 + 100)
const user = await fetchUser(id);
const orders = await fetchOrders(id);
const preferences = await fetchPreferences(id);

// Parallel: takes ~100ms total
const [user, orders, preferences] = await Promise.all([
  fetchUser(id),
  fetchOrders(id),
  fetchPreferences(id),
]);
```

如果这三个操作彼此独立，就并发地跑。Promise.all 会同时发起这三个，然后等它们全部完成。总耗时大约等于其中最慢的那一个，而不是三者之和。

彼此独立的并发操作用 Promise.all；后一个操作依赖前一个结果时，才用串行的 await。

**背压**

背压指的是生产者产出工作的速度快于消费者处理速度时发生的情况。放着不管，队列会无限膨胀，内存最终被耗尽。

正确的应对是给生产者发信号让它慢下来。在流式系统里，这意味着当可写流的缓冲区满了就暂停可读流；在队列系统里，这意味着给队列深度设上限，达到上限后拒绝新作业（或者阻塞生产者）。

无视背压，正是系统在高负载下 OOM（内存溢出）崩溃的原因。要显式地把它建进去。

**串起来看**

安全、扩展和并发不是彼此孤立的关注点。一个能水平扩展的系统需要无状态的请求处理，而这直接关联到你如何管理会话和认证。一个承受高并发负载的系统会暴露出只有在规模上来后才显形的竞态条件。一份为数据库减负的缓存，也需要被安全地失效掉，以免把陈旧数据跨租户地返回出去。

贯穿这三个领域的模式是同一个：理解其中的权衡，对自己的选择有意为之，并且从一开始就把这些属性建进系统，而不是等到出事之后再往上打补丁。
