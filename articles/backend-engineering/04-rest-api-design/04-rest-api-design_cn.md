## REST API 设计完全指南

REST API 支撑着几乎每一个现代 Web 应用，从加载你 Instagram 信息流的那个按钮，到电商网站的结算流程。可尽管它无处不在，设计砸了却出奇地容易。这篇文章会把（我尽力涵盖的）设计干净、可扩展、用起来舒服的 REST API 所需要知道的一切走一遍。

## REST 从哪来

1990 年代的 Web 增长得比任何人预料的都快，支撑它的基础设施在压力下开始不堪重负。2000 年，一位名叫 Roy Fielding 的计算机科学家提出了一套解决方案：一组他称之为 **REST** 的架构原则（全称 **Representational State Transfer**，表述性状态转移）。

这个名字听着晦涩，但拆开看很简单。一个资源（比如一份用户资料或一条商品条目）可以根据请求方的不同，以不同格式来表述（representation）——给移动 App 的是 JSON，给浏览器的是 HTML。状态（state）指的是该资源当前的快照。而转移（transfer）不过就是通过 HTTP 在客户端和服务端之间搬运这份表述的动作。

## 让一个 API 真正 RESTful 的六条约束

Fielding 不只是给 REST 起了个名字，他还给了它规则。一个自称 RESTful 的系统应该满足六条架构约束：

**1\. 客户端-服务端分离：** 客户端和服务端彼此独立。客户端拥有用户界面，服务端拥有数据和业务逻辑。任何一方都不需要知道另一方内部是怎么运作的。

**2\. 统一接口：** 各组件之间的所有交互都遵循一致的、标准化的契约。正是这种可预测性，让 REST API 能被任何地方的任何客户端轻松消费。

**3\. 分层架构：** 系统可以由多个层次组成，比如负载均衡器、缓存、代理，夹在客户端和服务端之间。每一层只知道紧挨着它的那一层，这同时提升了安全性和水平扩展能力。

**4\. 可缓存性：** 每个响应都必须明确声明自己能不能被缓存。恰当的缓存能极大地减少不必要的服务端负载，也让客户端体验更快。

**5\. 无状态：** 这大概是最重要的一条约束。服务端对之前的请求毫无记忆。客户端发来的每一个请求，都必须自带处理它所需的全部上下文——认证 token、用户 ID，全部。正是这一点让 REST 系统能轻松地水平扩展。

**6\. 按需代码**（可选）—— 服务端可以通过下发可执行代码来扩展客户端的行为，最明显的例子就是 JavaScript。这条约束是可选的，在实际的 API 设计里也很少被讨论。

## 设计干净、易读的 URL

一个设计良好的 URL 读起来应该几乎像一句话。在写下第一行代码之前，先把你的路由结构好好想清楚。

一个标准的 API URL 长这样：

[https://api.example.com/v1/users](https://api.example.com/v1/users)

每一段都有讲究：

- https：始终使用安全的协议。
- api.：一个专用子域名，能把你的 API 和主站 Web 应用分开。
- v1：从第一天起就给你的 API 加版本。等你发布破坏性变更时，直接升到 v2，而不会弄坏现有的客户端。
- users：资源名，**永远用复数名词**。

**永远用复数名词。** 即便你取的是单个条目，这个资源本身依然是某个集合的一部分。/users/123 是对的，/user/123 不对。

**用连字符，别用下划线。** URL 应该全小写，用连字符分隔单词。是 /blog-posts，不是 /blog\_posts 或 /blogPosts。

**用嵌套来表达层级。** 像 /organizations/42/projects 这样的路由，清楚地表达了「属于 42 号组织的那些项目」。嵌套应该反映数据模型里真实的从属关系，但别嵌套超过两三层，很快就会变得难以驾驭。

## HTTP 方法与幂等性这个概念

选对 HTTP 方法不只是遵循惯例，更是在传达意图。这里有个关键概念是**幂等性**：如果一个操作执行一次和执行一百次产生的服务端状态完全相同，它就是幂等的。

方法 用途 是否幂等？ GET - 获取资源 - 是 POST - 创建新资源 - 否 PUT - 整体替换资源 - 是 PATCH - 更新特定字段 - 是 DELETE - 删除资源 - 是

**POST 是唯一非幂等的方法。** 同一个 POST 请求发十次，你就会创建出十条各自带着不同 ID 的独立记录。这正是支付系统需要实现幂等键的原因——防止误重试造成重复扣款。

**PATCH 与 PUT** 是常见的困惑源。当客户端只想更新一两个字段时（比如改一个用户的邮箱），用 PATCH。当客户端发来的是整个资源的完整替换版本时，用 PUT。实践中，现代 API 里 PATCH 远比 PUT 常见。

## 当标准 CRUD 不够用时

CRUD 覆盖了大多数操作，但不是全部。那「克隆」一个项目怎么办？或者「归档」一个组织——这可能会连锁触发一大堆后台任务：通知成员、清理账单、锁定数据？

这些动作没法干净地映射成一次简单的更新。REST 处理这类情况的办法是，在具体资源路由的末尾追加一个**动词**，并且一律用 POST 请求：

POST /projects/123/clone POST /organizations/5/archive POST /invoices/88/send

这个模式既保持了意图的可读性，又与 REST 惯例保持一致。先标识资源，动作跟在后面。

## 构建高负载下不会崩的列表接口

一个返回条目列表的 GET 接口听起来很简单——直到你的数据库里有 50 万条记录，而某个客户端一次性把它们全要走。任何达到生产级水准的列表 API 都需要三样东西：

**分页：** 永远不要返回无上限的列表。把结果切成一页页，并在数据旁边附上元信息：

{ "data": \[...\], "total": 4823, "page": 2, "totalPages": 193 }

total 这个字段对要渲染「第 2 页，共 193 页」或者进度指示器的前端工程师特别有用。

**排序：** 让客户端通过查询参数来控制顺序：

GET /articles?sortBy=publishedAt&sortOrder=descending

务必在服务端定义合理的默认值。对大多数资源来说，按 created\_at 倒序是个稳妥的选择。

**过滤：** 客户端应该能够收窄结果，而不必把所有东西都取回来：

GET /users?status=active&role=admin

三者结合起来，一个接口就变得相当强大：

GET /orders?status=pending&sortBy=createdAt&sortOrder=ascending&page=1&limit=20

## 正确使用状态码

HTTP 状态码是你 API 契约的一部分。用错了，就等于逼着客户端去解析响应体，才能弄明白到底是不是出错了。

- **200 OK**：GET、PATCH、PUT 以及自定义动作的默认成功响应。
- **201 Created**：专门在 POST 创建了新资源时返回。它表明数据库里现在多了个新东西。
- **204 No Content**：DELETE 成功之后该给的响应。成功了，但没什么可返回的。
- **400 Bad Request**：客户端发来的数据格式有问题或者不合法。
- **401 Unauthorized**：请求缺少有效的认证凭据。
- **403 Forbidden**：客户端已经认证过了，但没有执行这个动作的权限。
- **404 Not Found**：某个具体的资源 ID 不存在。
- **409 Conflict**：请求与现有状态冲突（比如，试图用一个已存在的邮箱创建账号）。
- **422 Unprocessable Entity**：请求格式没问题，但没通过校验规则。
- **500 Internal Server Error**：服务端出岔子了。

有一条规则值得单独拎出来说：如果客户端请求一个列表接口，而过滤条件筛出来零条结果，应该返回 **200 加一个空数组，而不是 404**。空结果集不是错误，它是一个有效的答案。

## API 工程师的黄金法则

**从 UI 里挖出你的数据模型：** 在设计任何接口之前，先看看产品原型图。用户实际在跟哪些数据打交道？那些名词——用户、项目、任务、发票——就成了你的资源。那些动作就成了你的方法。

**内建合理的默认值：** 你的 API 会被凌晨两点疲惫不堪的工程师（比如我）写的客户端代码调用，他们忘了带分页参数。别崩。把每页条数默认成 10，把排序默认成最新优先，把新记录的状态默认成 active。合理的默认值能让你的 API 更有韧性、更宽容。

**毫不留情地强制一致性：** 所有 JSON 的键一律用 camelCase，任何地方、任何时候都不例外。如果一个字段在某个接口里叫 organizationName，它就不能在另一个接口里变成 org\_name 或 orgname。不一致会逼着每一个 API 使用方都去写额外的防御性代码，也会招来他们理所应当的怨气。

**用可交互的方式写文档：** 静态文档会过时。**Swagger（OpenAPI）** 这类工具能生成活的、可交互的文档，前端开发者可以直接在浏览器里对你的 API 发真实的测试请求。把文档当成一等交付物，而不是事后再补的东西。

**为使用者设计，而不是为数据库设计：** 你的 API 是一个产品。接口的形态应该反映客户端需要如何使用这些数据，而不是它们恰好在你数据库里是怎么存的。要抵抗住把原始表结构暴露出去的诱惑——那是实现细节，不是接口。
