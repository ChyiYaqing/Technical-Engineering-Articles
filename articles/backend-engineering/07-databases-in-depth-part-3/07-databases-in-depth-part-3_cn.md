## 数据库深入解析：第三部分（B 树变体与日志结构化存储）

各位好！第一、二部分从第一性原理出发把经典 B 树搭了起来：磁盘为什么逼着我们以页为单位思考、槽式页和单元是怎么工作的，以及分裂、合并和再平衡如何让树保持高度平衡。然而（很遗憾）经典 B 树并不是故事的终点。它有实实在在的弱点，尤其是在写放大、并发争用和缓存行为这几方面，而几十年的系统研究既产出了对 B 树自身的种种改良，也产出了一整套全然不同的存储范式——围绕日志而不是原地更新的树来构建。

第三部分把这个故事的两面都讲了。先讲那些针对经典设计的具体弱点而生的主要 B 树变体。然后讲日志结构化存储、LSM 树及其生态，它代表了现代存储引擎设计的另一大分支，并给我们从第一部分起就一直在绕的那些权衡收个尾。

## B 树变体

第二部分实现的那种经典 B 树是原地更新页的，靠预写日志来保证崩溃安全。这套做法效果不错，但它有代价：原地更新制造随机写，并发访问需要小心地加闩锁，而且朴素的实现未必和 CPU 缓存层级相处得好。下面每一种变体的存在，都是为了对付这些具体痛点中的一个或几个。

**写时复制 B 树**

第二部分简单提过它，但值得展开。在写时复制（COW）B 树里，修改从不原地碰已有的页。相反，被修改的页会作为一个全新副本写出去，而这个改动会向上传播：从该页到根这条路径上的每一个祖先也都会被复制并重写，因为每个祖先的子指针现在都得指向新页而不是旧页。等新根完全构造好，它会被原子地装上去——就一次指针交换——而在这次交换发生之前，此前整棵树保持不动、完全有效。

这近乎免费地提供了极强的崩溃一致性。如果写到一半崩溃，旧根依然指向一棵完好无损、有效的树，因为旧结构上的任何东西都没被改过。对树结构本身也不需要撤销日志，因为没有什么需要撤销——旧版本本来就还在那儿。

代价是自根到叶这条路径上的写放大。在一棵很深的树里改动一个键，可能需要重写从那个叶子直到根的每一页，尽管真正变化的只有叶子层的一个值。LMDB 这类系统采用了这个设计，它们赌的是崩溃安全上的简单性和读性能（读者永远不需要锁，因为它们只需从事务开始时那个有效的根去读）盖得过额外的写代价。这也和 MVCC 天然地联系起来了：旧的树版本可以短暂保留，好给长时间运行的读事务提供一份一致快照——精神上类似行级 MVCC，只是被用在了整棵树结构这个层面上。

**抽象节点更新（间接层）**

比完整的写时复制更渐进的一条替代路线，是在逻辑节点身份与物理页位置之间引入一个间接层，而不必每次写入都复制整棵树。父节点不再存一个直接指向子节点的磁盘偏移量，而是存一个逻辑页 ID，通过一张单独的映射表（有时叫页表或转换层）解析出子节点真正的物理位置。

这层抽象解锁了几项有用的能力。一个页可以在磁盘上被搬家（为了压缩、碎片整理，或者 SSD 上的磨损均衡），只需更新映射表里的一个条目，而不必重写每一个曾指向它的祖先。它还使部分写时复制这类技术成为可能：更新时只改映射表条目，而不必把新的物理页引用一路向上传播给每一个祖先。这就是下面要讲的 Bw 树这类更进阶设计的概念种子——在 Bw 树里，这种间接被推得远得多。

**惰性 B 树**

惰性 B 树建立在一个简单的观察之上：把每一个结构性改动（分裂、合并、再平衡）都立刻、同步地传播出去，往往比实际需要做的工作更多，在高写吞吐下尤其如此。惰性 B 树把这部分工作推迟，把结构维护批量化，而不是在每次操作时都急切地做掉。

这里一种常见的技术是在每个内部节点缓冲插入和删除（有时叫「缓冲树」方案），而不是每次都一路遍历到叶子。写入积攒在节点本地的缓冲区里，只有当缓冲区满了，这些被缓冲的操作才成批地被下推到相应的子节点。这就把树遍历的成本摊到了许多次写入上，而不是为每一次单独的插入都付出完整的自根到叶遍历代价。它的权衡是读路径变复杂了：一次读现在除了目标叶子之外，还可能需要检查下行途中多个层级上被缓冲的操作，以确保自己没有漏掉某个更近的缓冲写入。

惰性更新策略也以更简单的形式出现，比如在删除之后推迟叶子的再平衡（暂时留下一个未满的叶子，而不是立刻触发合并），赌的是很快就会有一次插入落到同一区域，让这次合并变得没必要。这就避免了在插入/删除交错的负载下叶子反复分裂又合并的「抖动」行为。

**FD 树（闪存磁盘树）**

FD 树是专门围绕闪存（SSD）的特性设计的，闪存的行为和机械盘非常不同。SSD 对随机读应付得还算好，但随机写相对昂贵，会加剧写放大并磨损闪存，因为闪存必须整块擦除再重写，而不能原地修改单个字节。

FD 树的应对办法，是把一个小的内存写缓冲（精神上类似下面 LSM 一节要讲的 memtable）与磁盘上一系列只读的有序段结合起来，这些段被组织成大小呈指数增长的多个层级，概念上类似 LSM 树的层级。新的写入在内存缓冲里积攒，一满就用顺序的、对批量友好的写入合并下沉到磁盘层级，而不是零散的随机写。每个磁盘层级还维护一个小的内存索引（一种「栅栏指针」结构，在最初的设计里则是分数级联结构），使得一次搜索能被高效地路由到正确的层级和位置，而不必线性地扫过每一层。

FD 树的核心洞见，本质上和 LSM 树更一般意义上的洞见是同一个：通过缓冲和批量归并，把随机写转换成顺序写，代价是读的复杂度上升，因为一次查找可能得检查多个层级。FD 树在历史上很重要，它是把这个权衡确立为「原地更新 B 树的一个严肃替代方案」的结构之一，其动机明确来自闪存硬件的特性。

**Bw 树（时髦词：无闩锁 B 树）**

Bw 树由微软研究院开发，用在早期版本的 Hekaton 里，后来也用在 SQL Server 和 Azure 的一些存储组件中，它攻的是另一个问题：闩锁争用。经典 B 树需要闩锁（在并发修改期间保护内存中页结构的短时锁），以防并发的读者和写者把一个正在更新的页搞坏。在高并发下，这种加闩锁会成为严重的瓶颈，在现代多核硬件上尤其如此——那里可能有几十上百个线程猛砸同样几个热页。

Bw 树的核心想法是彻底消灭闩锁：改用在一张映射表上做原子的比较并交换（CAS）操作，精神上和上面描述的间接层非常像，只是被推到了逻辑上的极致。更新不再原地修改页，而是被表示成一条小小的增量（delta）记录，只描述这次改动，然后通过 CAS 原子地插到映射表中该页逻辑 ID 所对应的那条增量链表的最前面。读者沿着这条增量链、连同基页一起遍历，重建出当前的逻辑状态。

当某条增量链变得太长时，它会被周期性地整合：基页和它累积的增量被归并成一个新的基页，映射表条目再一次通过 CAS 被原子地更新为指向这个新的整合页，整个过程全程不涉及任何锁。

这个设计做到了货真价实的无闩锁并发访问，在高度并行的硬件上是一项实打实的胜利，代价是实现复杂度显著上升（正确地推理无锁数据结构是出了名的困难），以及遍历增量链带来的一些读路径开销。Bw 树天然也支持在它下面铺一层日志结构化存储，因为页从不被原地修改，它们基于增量的更新可以以只追加的顺序方式刷到磁盘，这在概念上把它和本文后面要讲的日志结构化存储技术连了起来。

**缓存无关 B 树**

到目前为止讨论的一切都聚焦在磁盘/内存这条边界上。缓存无关（cache-oblivious）B 树针对的则是另一个虽然结构相似、但不同的问题：单台机器内部的多级缓存层级（L1、L2、L3 CPU 缓存，以及主存），其中每一级都有自己的容量，也有自己访问下一级的代价。

一个「缓存感知」的结构，会针对特定的缓存行和缓存大小参数显式调优。相比之下，一个「缓存无关」的结构，被设计成在完全不针对任何特定缓存大小调优的前提下，同时在内存层级的每一级上都取得接近最优的性能。这是通过递归的、自相似的布局做到的，最常见的是 van Emde Boas 布局：把一棵树递归地切成上半部和若干下半部，而这些半部各自又用同样的方案递归地布局下去，一直到单个元素。

由此产生的优雅性质是：无论某台硬件恰好有多大的缓存，这种递归细分总有某一层会天然地与那个缓存的大小对齐，也就是说树中一块连续的、缓存大小的片段本来就已经挨在一起放在内存里了，从而在层级的每一级上同时把缓存未命中降到最低，而这个结构自始至终都不需要事先知道缓存大小。

实践中，缓存无关 B 树在学术界和特定的高性能场景里用得比在主流生产数据库里多，因为真实世界的引擎往往用更简单的缓存感知调优（针对已知的常见硬件凭经验选定页和节点大小）就能拿到相当的实际收益。不过它背后的想法——结构布局的设计应当把整个内存层级都考虑进来，而不只是磁盘/内存这条边界——已经在更广的范围内影响了工程师思考数据布局的方式。

## 日志结构化存储

上面讲的一切，归根结底仍然是 B 树：一种围绕对页构成的树做原地（或写时复制）更新而组织起来的结构。日志结构化存储代表的是一套真正不同的哲学：不把数据组织成一棵可更新的树，而是把存储当作一个只追加的日志，并依靠后台进程随时间推移让这个日志保持可搜索、且空间上高效。

**核心想法：LSM 树**

日志结构化归并树（LSM 树）建立在一个第一、二部分已经预告过的简单洞见之上：无论在机械盘还是闪存上，顺序写都比随机写便宜得多。如果一个存储引擎能把它所有的写都转换成顺序追加，并把「为高效读取而组织这些数据」的工作推迟到一个独立的、批量化的后台过程里，它就能获得比 B 树高得多的写吞吐——而 B 树是通过分裂与合并，在每一次写入时同步地、内联地支付它的组织成本的。

LSM 树架构通常包含这几个组件：

**Memtable**：一个内存中的有序结构（常常是跳表，偶尔是小型的内存 B 树或红黑树），吸收所有新写入。因为它在内存里，这里的写极快，写入热路径上完全没有磁盘 I/O。

**预写日志**：既然 memtable 是易失的，磁盘上就有一份预写日志把每一次写入随发生随记下来，纯粹是顺序追加，这样万一进程在数据被刷盘之前崩溃，memtable 的内容还能被重建出来。

**SSTable（有序字符串表）**：一旦 memtable 达到某个大小阈值，它的内容就被刷到磁盘上，成为一个不可变的、有序的文件，也就是一个 SSTable。因为 memtable 本来就是有序的，这次刷盘本身就是一次简单高效的顺序写。SSTable 一旦写出，就再也不会被修改，这直接呼应了第一部分讨论过的不可变性原则。

**层级**：随着时间推移，磁盘上会积攒起许多 SSTable。LSM 树把它们组织成层级（通常编号为 L0、L1、L2 等等），每一层通常比它上面那一层大一个数量级。数据从 memtable 流入 L0，然后由一个后台压实进程周期性地把一层的 SSTable 归并进下一层：读取多个有序文件并把它们归并（很像归并排序里的合并步骤）成新的、更大的、依然有序的 SSTable，途中丢弃掉过期的或被覆盖的条目。

**读放大**

读是 LSM 树为其写优化设计付出代价的地方。因为同一个键的数据可能存在于 memtable 里、任意一个 L0 SSTable 里（L0 与更低的层级不同，它的各个文件之间键范围可以重叠，因为它们是各自独立地从 memtable 刷出来的），或者更低的每一层里恰好一个 SSTable 中，所以一次点查在最坏情况下可能需要检查许多个分散的位置，才能找到那个正确的、最新的键版本，或者确认这个键根本不存在。

这就叫**读放大**，即实际执行的磁盘读次数，与回答一次查询理论上最少所需的读次数之比。LSM 树用几种标准手段来缓解它：

- **布隆过滤器**：附在每个 SSTable 上的一种紧凑的概率性结构，能迅速回答「这个键肯定不在这个文件里」，且没有假阴性（尽管偶尔会有假阳性）。这让一次读能跳过绝大多数不含目标键的 SSTable，而不必真的把它们从磁盘上读出来。
- **栅栏指针 / 稀疏索引**：一份内存中的索引，记录每个 SSTable（或 SSTable 内每个块）的键范围，让一次读能直接跳到文件中相关的那一部分，而不是线性扫描它。
- **压实本身**：通过随时间推移把 SSTable 归并整合，压实直接减少了一次读可能需要检查的文件数，用后台的写入工作换取未来更低的读取代价。

**写放大**

有点反直觉的是，LSM 树尽管是为优化写而设计的，却仍然承受着另一种形式的写代价：**写放大**，也就是实际写到磁盘的总字节数（跨越最初的刷盘和后续所有的压实）与应用最初写入的逻辑字节数之比。一个键一旦被写下，可能会被重写好几次——从 L0 归并到 L1，再从 L1 到 L2，如此下去，每一轮压实都在物理上重写这个键的数据，哪怕它的逻辑值压根没变。

这在基于 LSM 的系统里是一项真实且常被低估的成本，也正是压实策略（下面会讲）之所以成为一个被积极研究的领域的主要原因，因为不同的压实策略在写放大、读放大和空间放大之间做的权衡截然不同。

**空间放大**

**空间放大**指的是 LSM 树消耗的磁盘空间超出它所持有数据逻辑大小的那部分。它有几个来源：尚未被压实回收的过期、被覆盖或已删除的条目，以及在数据被彻底归并下沉之前，维护多个层级上可能冗余的数据所带来的一般性开销。

读、写、空间这三种放大彼此之间存在根本性的张力，而这份张力正是 LSM 树设计中最具决定性的工程难题之一。压实得更激进（更早、更频繁地归并层级）会降低读放大和空间放大，因为数据更集中、过期条目更快被回收，但它会抬高写放大，因为数据被重写得更频繁。压实得更保守则反过来。调优一个基于 LSM 的系统，很大程度上就是在为给定负载选择它该落在这个三角形的哪个位置上。

**实现细节：压实策略**

生产级 LSM 实现中有两种压实策略占主导：

**分层压实（leveled compaction）**：每一层（L0 之外）的各个 SSTable 之间持有互不重叠、完全有序的键范围，而且每一层大致是它上面那一层的固定倍数大小。压实把第 N 层的一个（或一组）文件归并进第 N+1 层与之重叠的文件里。这个策略倾向于把空间放大和读放大压到最低（因为键范围不重叠，每层至多只需检查一个文件），代价是更高的写放大，因为数据每经过一层就被重写一次。RocksDB 和 LevelDB（名字已经暗示了）默认采用这个策略。

**按大小分层压实（size-tiered compaction）**：把大小相近的 SSTable 归到一组，等到攒够足够多同等大小的文件，就把它们归并成一个新的、更大的 SSTable，并不一定要在一层之内维持严格互不重叠的键范围。相比分层压实，这降低了写放大（数据被重写的频率更低），但同时抬高了读放大（可能需要检查更多键范围重叠的文件）和空间放大（同一时刻堆着更多尚未被压实的冗余数据）。Cassandra 历史上把它作为一个常见的默认选项，尤其适合写多的负载。

许多现代系统（RocksDB 尤其如此）两种策略都支持，让运维方根据自身负载的读写配比来选，还有一些较新的设计使用混合策略，在树的不同层级上行为不同。

**无序 LSM 存储**

有一种更特化的变体，放松了「每一层都必须严格有序、可以按序归并」这个假设。在无序（或部分无序）的 LSM 设计里，进来的写入可能按到达时间或按哈希分组，而不是按排序键，把完整排序的代价推迟到压实时；在某些设计里，则干脆放弃全局排序，转而在无序段之上叠一层二级索引结构。这拿更慢的、需要索引辅助的点查，换取更便宜的摄入，适用于那些以极高吞吐写入为主、读取相对稀少的负载，比如某些日志、遥测或事件摄入系统——在那里写吞吐在成本方程中的分量远比在典型 OLTP 负载中更重。

**LSM 树中的并发**

LSM 树在并发上有一个直接源自其不可变性原则的结构性优势。既然 SSTable 一经写出就再也不会被修改，那么访问某个 SSTable 的读者就永远不需要和写者协调——不存在某个写者正在对那个文件做什么的可能。这消除了整整一类闩锁复杂度，而正是那类复杂度催生了 B 树世界里 Bw 树这样的结构。

LSM 树里剩下的并发挑战集中在更窄的几处：协调对可变 memtable 的访问（一般用并发跳表或类似的轻锁结构来处理，因为 memtable 是唯一一个真正被原地修改的组件），以及协调压实（它需要安全地把新归并出的 SSTable 换进来、把旧的退役掉，而不打断正在进行中的读；通常用引用计数或基于纪元的回收方案来处理，这样一个 SSTable 就不会在还有读在用它的时候被物理删除）。

**日志叠加（log stacking）**

日志叠加指的是一个微妙但重要的问题，它出现在日志结构化存储引擎被叠在其他日志结构化系统之上的时候：一个基于 LSM 的数据库跑在一个日志结构化文件系统之上，或者跑在 SSD 自己的闪存转换层（FTL）之上——而 FTL 内部本身就是用日志结构化、写时复制的技术在管理闪存。

问题在于，每一层都独立地认为自己在为顺序写做优化、在管理自己的垃圾回收或压实，可把好几层这样的东西叠在一起，就可能产生复合的、冗余的开销。数据库的压实在逻辑层面上顺序地重写数据，下面的文件系统可能自己又在对这个「顺序」写模式做写时复制式的搬迁，再下面的 SSD FTL 又在为磨损均衡做它自己内部的日志结构化重映射和垃圾回收。每一层的优化尝试，最终可能与下一层或上一层相抵触，或者冗余地重复了它的工作——这个现象有时被非正式地称为「日志之上的日志」或者「叠加日志」问题，它是一个实实在在的意外写放大来源，尤其是在那些孤立地看任何单独一层都显得很高效的系统里。

**LLAMA 与用心的叠加**

LLAMA（一个无闩锁、日志结构化、访问方法感知的存储引擎，与 Bw 树的研究一同在微软开发）正是对这个日志叠加问题的直接回应。它没有把 Bw 树这样的无闩锁结构架在一个通用的、毫不知情的文件系统或块存储层之上，而是被设计成一个明确感知其上层访问方法（Bw 树那套增量链、页映射表结构）的存储层，从而能带着「上层实际上如何使用和作废数据」的直接认知，去管理刷盘、压实和空间回收。

这种「用心的叠加」思路——把存储栈中相邻的两层带着对彼此的认知去设计，而不是把每一层都当成完全不透明的黑盒——是较新的存储引擎研究里反复出现的主题。与其把各自独立优化的通用层叠起来（数据库架在通用文件系统上，通用文件系统架在通用块设备上）然后接受上面描述的那种复合开销，用心的叠加主张要么把层压扁合并（让数据库直接管理裸块设备或裸闪存，完全绕过文件系统层，一些特化系统就是这么做的），要么至少让相邻层对彼此的行为知情到足以避免冗余工作的程度，比如重复的垃圾回收轮次，或者对同一个逻辑改动重复记日志。

《数据库深入解析》到这里就结束啦！！

贯穿这三个部分、贯穿所讲每一个话题的，是一条一致的线索：物理约束（磁盘与内存的延迟差、以页为单位的 I/O、顺序访问与随机访问、CPU 缓存层级）驱动着数据库内部几乎每一个有意义的设计决策。经典 B 树、它那些更奇特的变体（写时复制、Bw 树、缓存无关布局），以及整个日志结构化存储家族（LSM 树、FD 树，以及围绕它们构建的层叠系统），归根结底都是对同一个底层问题的不同回答：既然搬运数据有真实的物理代价，你要怎样组织它，才能让读、写和空间占用各自都恰好高效到你的负载实际所需的程度。

不存在一个放之四海皆准的正确答案，只有权衡——读优化对上写优化，简单性对上原始吞吐，基于闩锁的正确性对上无锁的复杂度——而理解这些权衡（而不是背下哪个具体数据库用了哪个具体结构），才是你在评估陌生系统、或者做出自己的架构决策时真正能迁移过去的东西。这一点，比这三部分里讲过的任何单一结构都更重要，也才是把数据库挖到这么深的真正目的。
