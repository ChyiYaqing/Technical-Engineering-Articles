# 服务间通信

> 服务之间如何互相通信
>
> 原文：[https://x.com/Harry_The_Nerd/status/2081302031646806047](https://x.com/Harry_The_Nerd/status/2081302031646806047) · 2026-07-26

![封面图](https://pbs.twimg.com/media/HOItQ1gbgAA1nan.jpg)

第三部分讲了服务边界该画在哪。现在你有了一组独立的服务，它们需要互相通信，而通信方式决定了你的系统在真实故障条件下究竟有多强韧。前几部分的理论洁癖，正是在这里撞上生产环境的一地鸡毛。

## **同步与异步**

任何一次交互，第一个决策都是：调用方是否需要拿到响应才能继续。

当调用方的代码确实拿不到答案就走不下去时，用同步调用，比如在展示订单确认页之前先确认支付是否成功。当调用方可以继续往下走、让结果稍后到达时，用异步调用，比如结算之后发送确认邮件。

这里最常见的错误是处处默认用同步。它会悄悄把你的服务图变成一条链，链上最慢的一环决定了整个请求的速度和可用性。

## **REST**

REST 是对外 API 的默认选择。它简单、跑在普通 HTTP 上、人人都懂，每种语言和工具都能毫无摩擦地支持它。如果你要向外部客户端或第三方暴露 API，REST 几乎总是正确的起点。

## **gRPC**

对于延迟预算很紧的内部服务间调用，gRPC 通常是更好的选择。它用二进制协议而不是文本 JSON，通过 protobuf 预先定义带类型的契约，序列化和反序列化都更快。代价是可读性差、对浏览器或 curl 这类工具不友好——而这恰恰是它比公开 API 更适合内部流量的原因。

## **GraphQL**

GraphQL 属于边缘层，作为聚合层服务于需要灵活查询的客户端，典型场景是移动端或 Web 前端在一次请求里把多个后端服务的数据拼在一起。它不适合内部的服务间通信。在那里用它只会增加复杂度，却没解决你真正遇到的问题——因为你的内部服务本来就很清楚彼此需要什么形态的数据。

## **消息队列**

消息队列把一条消息投递给一个消费者。它适合任务分发和削峰填谷，比如把图片处理任务分发给一组 worker，或者吸收一波写入洪峰，让下游系统能按稳定速率处理，而不是被冲垮。

## **事件流**

事件流把一个事件投递给多个消费者，而且通常会保留一段可回放的事件历史。当多个服务各自独立地关心同一件事发生时，它就是合适的工具，比如一个「订单已创建」事件，库存服务、通知服务和分析服务都需要各按各的方式做出反应。

它和队列的核心区别在于扇出。队列是一条消息被一个 worker 取走。流是一个事件被每一个感兴趣的方观察到。

## **命令与事件**

命令是让另一个服务去做某件具体的事，比如「扣款」。命令会把发送方和接收方耦合起来，因为发送方必须明确知道谁该处理它、以及自己期待什么返回。

事件陈述的是某件事已经发生了，比如「款项已扣」。事件让发送方和接收方解耦，因为发送方不需要知道也不需要在意谁在听。任何感兴趣的人都可以订阅。

在可能的情况下优先用事件而非命令，是降低服务间耦合最简单的办法之一，因为这意味着以后新增消费者时，完全不用碰产生该事件的那个服务。

## **超时**

每一次对其他服务的调用都要设超时，没有例外。没有超时的调用可能无限期挂起，在等待期间一直占着线程或连接——一个服务变慢就是这样悄悄演变成所有调用它的服务集体故障的。

**重试**

重试只应该用在幂等操作上，也就是无论执行多少次结果都相同的操作。对「创建订单」这类非幂等操作，在没有幂等键的情况下重试，会制造重复数据。

真要重试时，用带抖动的退避：每次尝试之间等待的时间逐步拉长，并加入一些随机性，避免大量客户端在同一时刻一起重试，把它们本想访问的服务压垮。重试次数控制在两三次以内。超过这个数，你通常只是在给一个已经吃力的服务继续加压，同时推迟一次注定要发生的失败。

## **熔断器**

熔断器通过跟踪对某个依赖的调用是成功还是失败，在失败率越过阈值后彻底停止调用，从而防止级联故障。

它有三个状态。关闭（Closed）表示调用正常通过。打开（Open）表示调用立即失败，连网络调用都不发起，给那个吃力的依赖留出恢复空间。半开（Half-Open）表示熔断器放行少量试探调用，检查依赖是否已经恢复：成功就回到关闭，失败就回到打开。

## **舱壁隔离**

舱壁隔离是把某个依赖使用的资源池，和另一个依赖使用的资源池隔开，思路和船体上的水密舱一样。如果某个依赖变慢，它只应该耗尽自己的连接池或线程池，而不该耗尽你服务里其他所有调用都依赖的共享池。

## **背压**

背压的意思是拒绝超额负载，而不是试图全盘吸收然后崩掉。具体形式包括有界队列——队列有最大长度，满了就拒绝新任务——以及限流——服务限定自己每秒接受多少请求。干脆地拒绝一个请求并给出明确错误，远好过接下来慢慢把自己拖垮。

## **契约版本管理**

服务是独立部署的，这意味着调用方和被调用方很少在同一时刻运行完全相同版本的契约。让这件事跑得通的规则是：只加字段，永远不删字段。在响应里加一个新字段是安全的，因为老客户端会直接忽略它。删除或重命名字段，则会搞坏每一个还依赖它的客户端。

这种向后兼容性，才是让独立部署在实践中真正可行的东西。没有它，你又回到了跨团队协调发版的老路，那当初拆分服务的意义就全没了。

## **关联 ID**

一次用户请求在被完整处理之前，可能要跳过很多个服务。关联 ID（correlation ID）是在最开始的入口处附加到请求上的唯一标识，并随每一次下游调用一路传递下去，这样涉及的每个服务里的每一行日志、每一段 trace、每一个错误，都能被追溯回最初那一次请求。

没有它，调试一次跨服务故障就意味着手工拼凑时间戳，靠猜来判断哪些日志属于同一件事。有了它，你一次查询就能捞出所有相关的日志行。
