# 数据所有权与读模型

> 没有共享数据库可依靠时，服务如何处理数据
>
> 原文：[https://x.com/Harry_The_Nerd/status/2081673770092433631](https://x.com/Harry_The_Nerd/status/2081673770092433631) · 2026-07-27

![封面图](https://pbs.twimg.com/media/HOOW29raIAAFUmE.jpg)

第四部分讲了服务之间怎么通信。这一部分讲更难的事：当没有共享数据库可以依靠时，服务如何处理数据。微服务迁移通常就是在这里真正开始变难，因为第三部分那些干净的服务边界，会在这里撞上一个现实——用户往往需要同时看到来自多个服务的数据。

## **每服务一库**

这一条没得商量。每个服务独占地拥有自己的数据存储，其他服务一律不得直接碰它。正是这一点让独立部署真正成为可能：只要保持 API 契约稳定，一个服务就可以改表结构、换数据库技术、加索引，不用征求任何人同意。

## **共享数据库**

上一条的反面，也是团队意外造出分布式单体应用最常见的路径之一。如果两个服务共用一个数据库，其中一个改表结构就可能悄无声息地搞坏另一个，部署必须联动，而你付出了网络开销，却没换来你本想买的任何独立性。如果你在系统里发现了共享数据库，那说明有一条边界画错了地方。

## **API 组合**

把多个服务的数据合到一起最简单的办法：分别调用每个服务，在需要的地方把结果合并，通常是在 API 网关或客户端本身。这种做法容易理解，在低流量、低复杂度的场景下没问题。但一旦你要在一次请求里组合很多个服务的数据，或者请求量很高，它就不好使了——因为你现在要串行或并行发起好几次网络调用才能回答一个问题，而整个响应的速度和可靠性，取决于其中最慢、最不可靠的那个服务。

## **物化视图**

物化视图通过监听拥有数据的那些服务发出的事件，提前把跨服务数据算好，而不是每次读取时都同步去调用它们。这带来很高的读性能，因为数据已经组装好、就放在本地；代价是最终一致——视图会比真相来源滞后一点，滞后时长取决于事件到达并被处理需要多久。

## **数据冗余**

一旦你接受了物化视图和读模型，你就是把数据冗余当成一个刻意的设计选择，而不是一次意外。任何一份数据仍然有且只有一个真相来源，由一个服务拥有，但其他服务被允许保留自己需要的本地副本，通过事件保持同步。用一些冗余数据换取独立性和读性能——这个权衡，是微服务数据体系实际运转方式的核心。

## **最终一致性**

这是微服务系统里数据的默认状态，对多数读取场景来说是可以接受的。用户晚一两秒才看到订单状态更新，很少构成真正的问题。但对金融交易就不可接受了——短暂出错的代价（重复扣款、余额不对）高到你需要更强的保证，这通常意味着让那条特定的数据路径保持同步和强一致，而不是最终一致。

## **读己所写**

有一个常见且令人错愕的问题：用户更新了某样东西，紧接着却看不到更新生效，因为他们下一次读取落到了一个还没追上的副本或读模型上。解决办法是：在写入之后的一小段时间窗口内，把这位写入用户自己的读请求路由到真相来源，而其他所有人可以继续读那份更快的、最终一致的副本。

**CQRS**

命令查询职责分离（CQRS）指的是把写模型和读模型彻底分开，而不是两边共用一个模型。当读写模式差异极大时，它是合理的，比如一个系统写入时有复杂的校验规则，但读取需要极快、高度反范式化。它带来的复杂度相当可观，所以只有当两种模式的差距大到确实需要时才值得动用，而不该当成默认架构。

## **参考数据**

当一个服务需要它并不拥有的数据时——比如处理订单时需要客户的收货地址——主要有三种做法，各自在数据新鲜度上做了不同的权衡。事件时快照，是在相关事件发生时把当时的数据抓下来，简单但可能过期。事件驱动缓存，是订阅变更并持续更新本地副本，更新鲜但要多一套基础设施。同步 API 调用，是每次都直接问拥有该数据的服务，永远最新，但会在请求时把两个服务耦合起来，还增加延迟。选哪一种，完全取决于这份数据到底需要多新鲜。

## **搜索索引**

搜索是派生读模型的一个好例子。搜索索引通常由来自多个服务的事件喂养，比如商品目录服务和库存服务共同喂给一个搜索索引，这样搜索就能返回完整、最新的结果，而不必在每次搜索请求时直接查询多个服务。

## **缓存所有权**

拥有数据的那个服务，同时也拥有该数据任何缓存的失效逻辑。其他服务或分层可以持有并使用缓存副本，但它们绝不该负责判断副本什么时候过期。这个责任必须落在真相来源身上，否则你会得到一堆悄悄漂移的缓存，而没人明确为修复它负责。

## **报表**

分析和报表查询应该跑在一个独立的分析型存储上，由业务服务发出的事件喂养，绝不要直接跑在业务数据库上。业务数据库是为线上应用的事务负载调优的。沉重的分析查询压上去，会和线上负载争抢同样的资源，拖慢真实用户的体验——而这恰恰是一个好架构应该防住的事情。

## **表结构迁移**

因为一个服务的表结构和它的消费者是独立部署的，表结构变更必须能安全地渐进上线，而不是一次性切换。扩展-收缩（expand-contract）模式处理的就是这件事：先在旧字段或旧表旁边加上新的，然后把每一个消费者都迁移到新版本，等所有消费者都迁完了，才移除旧的。直接跳到破坏性变更，等于假设所有消费者会齐步更新，而这恰恰是微服务设计要避免的假设。
