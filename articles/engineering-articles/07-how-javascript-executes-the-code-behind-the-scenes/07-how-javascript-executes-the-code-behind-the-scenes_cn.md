# JavaScript 如何执行代码——幕后揭秘

> JavaScript 引擎在底层是如何执行代码的。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2075158256826335454](https://x.com/Harry_The_Nerd/status/2075158256826335454) · 2026-07-09

![封面图](https://pbs.twimg.com/media/HMtSMWIasAAx-KI.jpg)

JavaScript 表面看起来很简单。你写几行代码，点一下运行，它就跑起来了。但在底层，有一整条流水线把你可读的源代码变成 CPU 真正能执行的机器指令。我们就按照 V8（驱动 Chrome 和 Node.js 的引擎）的做法，一个阶段一个阶段地拆开来看。

## 阶段 1：源代码

一切都从你的 **.js** 文件开始。它只是躺在磁盘上的纯文本。引擎的任务就是把这段文本变成机器能理解的东西。这个过程分好几个阶段完成，没有哪一步是「一次性把所有东西都编译完」。JavaScript 引擎很聪明，只在恰当的时机做恰好够用的工作。

## 阶段 2：词法分析（分词）

在做任何别的事情之前，引擎会逐个字符地读取你的原始文本，把它切成一个个小块，这些小块叫做 token。这个过程称为分词（tokenizing）或词法分析。

举个例子，下面这一行：

```javascript
let x = 10 + 5;
```

会被切成这样一串 token：

let, x, =, 10, +, 5, ;

每个 token 都有一个类型（关键字、标识符、数字、运算符、标点）和一个值。分词器此时还不关心语义，它只是把文本切成有意义的碎片，顺手丢掉多余的空白和注释。

## 阶段 3：语法分析与抽象语法树（AST）

有了 token 之后，引擎需要理解代码的结构和语法。这就轮到解析器（parser）登场了。

解析器接收这串扁平的 token 列表，构建出一棵树形结构，叫做抽象语法树（AST）。这棵树表示程序的语法结构。于是 let x = 10 + 5; 就变成了类似这样的东西：

![](https://pbs.twimg.com/media/HMxxG-kb0AAXisI.jpg)

代码里的每一条语句、每一个表达式和声明，都会成为这棵树上的一个节点。Babel、ESLint 这类工具用的也是同一套思路，它们都是靠生成并遍历 AST 来工作的。

出于性能考虑，V8 实际上会做两遍。第一遍是快速的「预解析」，只扫描函数体而不完整解析（跳过那些不会立即调用的函数，因为解析开销不小，而很多函数根本不会被执行）。等到某个函数真的即将执行时，才对它做完整解析。这叫做惰性解析（lazy parsing），也是 JS 引擎哪怕面对巨型代码库也能快速启动的原因之一。

## 阶段 4：从 AST 到字节码

很多人在这里会犯迷糊，因为他们以为 JS 就是直接从 AST 一行行解释执行的。现代引擎并不这么干。直接解释一棵树很慢，因为你得不停地跟着指针跳转、不停地检查节点类型。

V8 的做法是引入一个叫 Ignition 的组件，也就是解释器。Ignition 接收 AST，把它编译成一种更简单、更紧凑的形式——字节码（bytecode）。

字节码不是机器码。它是一套层次更低、引擎专有的指令集，可以理解为介于你的 JS 代码和真正的 CPU 指令之间的中间语言。字节码指令长这样：

LdaSmi \[10\] Star r0 LdaSmi \[5\] Add r0

这些都是小而通用的指令，比如「加载一个值」「把两个寄存器相加」「存入某个变量」。字节码很紧凑，生成快，开始执行也快。这就是为什么 JS 几乎可以立刻开跑，而不用像 C++ 那样先等一次完整而沉重的编译。

## 阶段 5：解释执行开始

Ignition 会立刻用一个解释器循环开始执行这些字节码。这让你的代码很快跑起来，但从长期看，解释执行并不是运行代码最快的方式，因为每条指令被逐条解释时都有额外开销。

在解释的同时，引擎还干了件聪明事：它会在运行过程中收集关于你代码的信息。这叫做性能剖析（profiling），或者说收集类型反馈。它会观察这些东西：

- 实际流入某个函数的值都是什么类型（数字、字符串、对象）
- 哪些函数被反复调用（热点函数）
- 对象有什么样的形状（它们的属性和结构）

这些信息在下一个阶段会变得非常重要。

## 阶段 6：JIT 编译器介入

JIT 是即时编译（Just In Time compilation）的缩写。这是现代 JS 引擎真正的性能秘诀。引擎不会一上来就把所有东西编译成机器码（那样启动很慢，而且对只运行一次的代码来说是浪费），而是先等待、先观察。

如果某个函数被调用了很多次（V8 把它们叫做「热点函数」），引擎就会判断值得花额外的力气去优化它。这时 V8 的优化编译器 TurboFan 就登场了。

TurboFan 拿到字节码加上此前收集的全部类型反馈，把这个热点函数直接编译成高度优化的机器码，也就是 CPU 原生执行的二进制指令。不再需要一步步解释，CPU 直接执行就行。

这份优化过的机器码之所以快得多，是因为它可以基于观察到的情况做出假设。举个例子，如果某个函数一直接收数字作为参数，TurboFan 就能生成跳过 JS 通常需要的那些类型检查、直接做原始数值运算的机器码。

## 阶段 7：去优化（安全网）

问题就在这里。JavaScript 是动态类型的，所以 JIT 编译器做出的那些假设，之后可能被证明是错的。假设某个函数是按「总是收到数字」优化的，结果后来有人用字符串调用了它。

这种情况发生时，引擎不能继续跑那份优化后的机器码，否则结果就错了。于是它把优化版本丢掉，退回到较慢的字节码解释器。这叫做去优化（deoptimization），或者说「bailing out」。

如果这个函数之后又稳定回一致的类型，它还可以被重新优化。这也是为什么在 JS 里写风格一致、可预测的代码（类型一致、对象形状一致）通常跑得更快：这让 JIT 编译器可以对自己的优化保持信心，而不用不停地退回去。

## 阶段 8：隐藏类与内联缓存

还有两个概念让整套系统变得飞快：

**隐藏类（Hidden classes）：** JS 对象不像 Java 或 C++ 里的类那样有固定结构。但在底层，V8 会根据对象的属性结构，悄悄给它们分配隐藏类（也叫「shapes」）。两个属性相同、顺序也相同的对象会共享同一个隐藏类。这让引擎几乎可以把 JS 对象当成布局固定的结构体来处理，比每次都去哈希表里查属性快得多。

**内联缓存（Inline caching）：** 当引擎反复看到同一个操作，比如访问 [obj.name](https://x.com/Harry_The_Nerd/status/obj.name)，它会基于隐藏类把该属性的位置缓存下来，这样下一次就能直接跳到那个内存地址，而不用做一次完整查找。对于 JS 代码里极其常见的重复属性访问来说，这是巨大的提速。

## 把整条链路串起来

下面是完整的流水线顺序：

源代码（.js 文件）-\> 分词器（词法分析，产出 token）-\> 解析器（产出抽象语法树）-\> Ignition（把 AST 编译成字节码并解释执行）-\> 剖析器（运行时收集类型反馈）-\> TurboFan（把热点字节码 JIT 编译成优化后的机器码）-\> CPU 直接执行机器码 -\>（如果假设被打破）去优化，退回字节码

整套系统之所以存在，是因为一个权衡。纯解释器运行慢但启动快。纯编译器运行快但启动慢（因为执行任何东西之前都得先完整编译）。JS 引擎两头的好处都要：先用解释器实现即时执行，再把热点代码路径动态升级成编译后的机器码，同时保留一旦优化被证伪就退回去的能力。

这也是为什么 JS 里的微基准测试可能会误导人。只跑一次的代码，和在紧密循环里跑上千次的代码，表现差别极大，因为后者能吃到 JIT 优化的全部红利，而前者根本没离开过解释器。
