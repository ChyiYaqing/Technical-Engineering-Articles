## Netflix 机器学习推荐系统：高层设计

## 问题定义

Netflix 为数亿用户提供电影、剧集和纪录片服务。除了存储和流式传输内容之外，核心难题是：在用户打开 App 的那一刻，决定给他看什么，而且每一次都要显得个性化、相关、新鲜。

一种朴素的做法是把用户严格分桶：看电影的只推电影，看剧集的只推剧集。但这会造成内容孤岛，扼杀内容发现。更好的做法是「**混合加权推荐模型**」。如果一个用户主要看电影，那他的推荐组合大概是 70% 电影、15% 剧集、15% 纪录片。这样既尊重了他的偏好，又不会把他锁死在孤岛里。

支撑整个系统的两个机器学习指标是 **recall（召回率）**——我们有没有把用户会喜欢的内容捞出来？以及 **precision（准确率）**——我们捞出来的这些内容里，他真正互动了多少？这两个目标驱动着架构的每一层。

## 规模与容量估算

在设计系统之前，先把数字定下来。

**流量**

- 日活用户（DAU）：2 亿
- 内容库：10 万个标题（电影 + 剧集 + 纪录片）
- 每个用户每天的交互次数：约 50 次事件
- 每天的原始交互数据：2 亿 x 50 x 1KB = 10TB/天
- 每个用户每天的会话数：约 2 次，每次会话加载一次首页
- 推荐请求量：2 亿 x 2 = 4 亿请求/天 -\> 平均约 4,600 RPS，峰值约 10K RPS

**存储**

- 内容元数据：10 万 x 1KB = **100MB**（很小，可以完全缓存在内存里）
- 视频：存在 S3，通过 CDN 分发
- 物品嵌入向量：10 万个标题 x 128 维 x 4 字节 = **约 50MB**（完全放得进内存）
- 用户嵌入向量：2 亿用户 x 128 维 x 4 字节 = **约 100GB**（存在 Redis 或 DynamoDB，定期更新）
- 行为数据湖：Cassandra，每天摄入 10TB 原始信号

**延迟预算**

- Netflix 首页必须在 200ms 内加载完。这意味着推荐流水线不可能在每次请求时实时跑一遍。推荐结果必须**预先计算好并缓存起来**，首页拉取只是一次缓存读取。

## **应对新用户：冷启动策略**

一个全新用户没有观看历史、没有会话数据、没有任何行为信号。用三种策略可以平滑地应对。

**1\. 显式的品类引导**注册时，给用户展示 5 到 8 张品类卡片（爱情喜剧、惊悚片等），让他挑感兴趣的。这是一种轻量的显式信号。整个引导流程必须控制在最多 3 到 5 次点击以内，因为一旦让人觉得像在填表，流失率就会很高。

**2\. 全球和区域的热门内容**大多数新用户来 Netflix 是冲着热门、知名的内容来的。把全球热门标题（全球 Top 10）和历史上的名作推给他们，能立刻带来有用的体验。社会认同能降低选择疲劳。

**3\. 地理位置和设备信号**在任何交互发生之前，用户的地理位置就已经是很强的隐式信号了。区域内容偏好是真实存在的：印度偏向宝莱坞和本地语言内容，韩国偏向韩剧，等等。CDN 以低延迟分发这些区域内容。注册时的设备类型（晚上 10 点在印度用手机）也是一个弱但有用的信号。

**过渡到个性化**只要用户看了 2 到 3 个内容，行为信号就开始积累。系统会逐渐把协同过滤混进来。随着个人数据增多，冷启动模型平滑地退居其次。

## **行为信号**

光靠原始点击是很弱的信号。系统必须捕捉一组更丰富的用户行为，才能构建准确的偏好画像。

- **会话观看时长**：花了多少小时在看，而不只是打开了什么
- **完播率**：90% 的完播是很强的正向信号；看到 20 分钟就退出则是负向信号
- **重复观看**：重看一个标题是系统里最强的偏好信号之一
- **显式评分**：点赞／点踩，稀疏但质量很高
- **搜索查询**：直接的意图信号。搜索「犯罪惊悚」明确地告诉你品类偏好
- **加入片单但没有播放**：带阻力的兴趣信号
- **时段和设备**：早上用手机说明偏短小或轻松的内容；晚上用电视说明偏长篇沉浸式内容
- **跳过片头／跳过前情提要的行为**：反映投入深度和熟悉程度

所有这些信号都由 **Data Aggregator Service** 摄取，并以 user\_id + timestamp 为键写入 Cassandra。这是一种写密集、类时序的负载，而这正是 Cassandra 在这种规模下的设计初衷。

## **什么是嵌入向量？**

在描述机器学习流水线之前，有必要先理解嵌入向量，因为它是整个推荐系统的基石。

机器无法理解「Breaking Bad」或「The Big Bang Theory」这些标题。它需要一种数值表示，来刻画这个标题的含义和特征。嵌入向量就是高维空间中的一个稠密数字向量，通常是 128 维或 256 维，用来编码一个实体的语义属性。

举个例子：

Breaking Bad = \[0.82, 0.11, 0.94, 0.03, ...\]（128 个数字） Narcos = \[0.79, 0.13, 0.91, 0.06, ...\]（128 个数字）

这两个向量在嵌入空间里彼此靠得很近，因为它们都是高张力的犯罪剧，都涉及毒品题材，观众画像也相似。**相似的内容聚在一起，相似的用户也聚在一起。**推荐于是变成了这个向量空间中的最近邻搜索问题。

有两类嵌入向量支撑着这个系统：

- **物品嵌入向量**：每个标题一个向量。10 万个标题 x 128 维 x 4 字节 = 约 50MB。完全放得进内存。
- **用户嵌入向量**：每个用户一个向量，由他的行为历史构建而成。2 亿用户 x 128 维 x 4 字节 = 约 100GB。存在 Redis 里，按固定节奏更新。

## 系统架构：三个核心服务

流量经过 API 网关和负载均衡器之后，推荐系统由三个服务构成。

**1\. User Service**

负责用户资料管理。用户打开 App 时，User Service 触发 Recommendation Service 去填充这个用户的首页。Kafka 位于 User Service 和 Recommendation Service 之间，把资料更新事件和推荐刷新周期解耦。这样登录量突增时，也不会把推荐流水线压垮。

**2\. Recommendation Service**

这是整个系统的心脏。它跑的是一条**两阶段机器学习流水线**：先做候选筛选，再做排序。

**3\. Data Aggregator Service**

从用户会话中消费所有行为信号（点击、会话时长、观看时长、重复观看、加入片单等），写入 Cassandra。机器学习模型就在这些数据上训练。这里同样用 Kafka 来给高吞吐的事件流做缓冲，然后再落到存储里。

## **两阶段机器学习流水线**

这是推荐系统的核心。在 10K RPS、200ms 预算的条件下，用单个模型直接从 10 万个标题算出一个 20 条的排序列表，计算上根本行不通。两阶段方案干净利落地解决了这个问题。

**阶段一：候选筛选器（召回模型）**

**目标**：把 10 万个标题缩减到针对该用户的前 100 个候选。

这一阶段以召回率为先。它不能漏掉用户会喜欢的内容。这里速度比排序精度更重要。

采用的机制是**近似最近邻（ANN）搜索**。把用户的嵌入向量拿去和向量空间中所有物品嵌入向量比对，取出最接近的 100 个标题。**FAISS**（Facebook AI Similarity Search）或 **Pinecone** 这类工具，即使在 10 万个向量上也能在毫秒级完成这次搜索。

协同过滤也在这一阶段发挥作用：看过内容 X 的用户也看了 Y。这让召回范围超出了单个用户自己的直接历史。

**流程：用户嵌入向量 -\> 在物品嵌入向量上做 ANN 搜索 -\> 前 100 个候选**

**阶段二：排序器（准确率模型）**

**目标**：给这 100 个候选打分排序，收敛到最终展示的前 20 个标题。

这一阶段以准确率为先。它引入更丰富、计算代价更高的特征，送进一个更重的神经网络模型。特征包括：

- 用户观看历史和偏好分
- 内容新鲜度和上线日期
- 时段和设备类型
- 相似用户对缩略图的点击率
- 协同邻居中相似内容的完播率

这 100 个候选每个都会得到一个分数。取前 20 个写入 **Redis**，以 user\_id 为键。

流程：100 个候选 + 丰富特征 -\> 神经网络排序器 -\> 前 20 个分数 -\> Redis

**画像填充**

当 User Service 需要填充首页时，它对 Redis 发一次 **MGET**，取出该用户预先算好的前 20 条。这是一次亚毫秒级的操作。200ms 的首页预算轻松达标，因为请求时刻根本没有机器学习推理发生。

**数据存储与模型新鲜度：Lambda 架构**

Cassandra 大规模存储所有行为数据。但随之出现两个问题：深度的模型重训练要花好几个小时，没法持续跑；而实时行为（10 分钟前刚看了一部惊悚片）应该立刻影响下一次推荐。

**Lambda 架构**同时解决了这两点。

**批处理层**每 24 小时在完整的 Cassandra 数据集上做一次全量模型重训练。这是深度的一遍：用户嵌入向量和物品嵌入向量被完全重新计算，捕捉长期模式和季节性变化。这个任务在夜间以定时作业的方式运行。

**速度层**一个轻量模型跑在实时 Kafka 流上。它捕捉最近的信号（上一次会话的观看行为），对用户嵌入向量做增量更新，不必等到下一次全量重训。如果你刚一口气看了三部惊悚片，你的推荐会在几分钟内偏向惊悚片，而不是等到第二天。

两者合起来：

- 批处理层 -\> 深度与准确性
- 速度层 -\> 新鲜度与响应速度

多样性注入：避免回音室

一个纯粹优化准确率的排序器，最终会给用户推 20 部犯罪惊悚片，因为那是他最强的偏好。这就形成了回音室，扼杀内容发现，长期还会推高流失率。

排序器输出和写入 Redis 之间，夹着一层**排序后多样性层**。它用几种策略对最终的 20 条做重排和限额。

**品类封顶**：不管偏好分多高，单一品类占据的位置都不能超过 20 个中的 5 到 6 个。

**新鲜度注入**：刻意留出 2 到 3 个位置给用户从未接触过的标题，哪怕它们的排序分略低一些。长期看，这能推动小众内容的发现。

**探索与利用（Bandit 方法）**：85% 的位置用来利用已知偏好，15% 用来探索新领域。模型从探索位置上的互动情况学习，逐步把新偏好吸收进用户嵌入向量。

**基于货架的多样性**：Netflix 的首页不是一个 20 条的单一列表，而是组织成一排排横向货架：「因为你看过 X」「印度正在热播」「新上线」「今日 Top 10」。每个货架有自己的多样性和品类规则。这既是解决回音室问题的用户体验方案，也是算法方案。

**端到端请求流程**

用户打开 Netflix App | v API 网关 -\> 负载均衡器 | v User Service（资料查询）| \[Kafka 事件\] | v Recommendation Service | v Redis 查询（用 user\_id MGET 取前 20 条）<\-- 预先算好的，亚毫秒级 | v 用个性化货架内容渲染首页 |（后台进行）| v Data Aggregator Service 摄取会话信号 -\> Kafka -\> Cassandra | v 批量重训练（每 24 小时）+ 速度层（实时流）| v 更新后的用户嵌入向量 -\> 候选筛选器 -\> 排序器 -\> 多样性层 -\> Redis

技术选型总结

- **API 网关 + 负载均衡器**：入口，流量分发
- **Kafka**：服务间解耦，为高吞吐事件流做缓冲
- **Cassandra**：行为数据湖，以 user\_id + timestamp 为键的写密集时序事件
- **FAISS / Pinecone**：在向量空间中做 ANN 搜索，生成候选
- **Redis**：每个用户预先算好的前 20 条推荐，亚毫秒级 MGET 读取
- **S3 + CDN**：视频存储与分发，同时以区域缓存提供缩略图和预告片
- **Lambda 架构**：批处理层（24 小时重训练）+ 速度层（实时 Kafka 流更新）
