# 设计 Bit.ly 和 Pastebin

> 手把手拆解短链接服务与文本分享服务的设计。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2044672371546877964](https://x.com/Harry_The_Nerd/status/2044672371546877964) · 2026-04-16

![封面图](https://pbs.twimg.com/media/HF-TxWpb0AAmmTe.jpg)

各位大佬好！我要开一个高层设计系列。入门级面试题里最常见的两道，就是 [Bit.ly](https://x.com/Harry_The_Nerd/status/Bit.ly) 和 Pastebin。表面上看它们挺像，都是接收一个输入、返回一个短链接。但架构上的差别要深得多。下面是这两个系统的完整拆解。

**设计 [Bit.ly](https://x.com/Harry_The_Nerd/status/Bit.ly) —— 短链接服务**

在动手设计之前，先搞清楚那些可怕的面试官到底想看什么。他们想看到的结构是：1. 功能需求 2. 非功能需求（延迟、规模、可用性）3. 粗略估算 4. 高层设计 5. 针对瓶颈的深入讨论。

**[Bit.ly](https://x.com/Harry_The_Nerd/status/Bit.ly) 的功能需求**

1\. 把长 URL 缩短 2. 通过短 URL 跳回原始 URL 3. 数据分析（说实话，大多数面试里这一条是可选的）

**系统性质**

这是一个读多写少的系统，因为一个 URL 只缩短一次，却会被访问很多次。就这一个观察，决定了你后面大部分设计决策：缓存、只读副本、服务拆分。

**粗略估算** 我们假设有 1000 万日活用户（DAU）。

按 1000 万 DAU、10 亿条历史 URL 计算，把一天的秒数取整成 10 万秒，总量大约是每秒 10,000 次请求。但要把读和写分开看——写大概只占流量的 1%（约 100 req/s），读占剩下的 99%（约 9,900 req/s）。永远要把这两者分开，它们的扩展方式是独立的。

**接下来是短链接的生成**

这里有个常见错误：用 MD5 或 SHA-256 然后取前 6 个字符。两个不同的 URL 可能产生相同的 6 字符前缀，这就是哈希冲突。

改用自增 ID 的 Base62 编码。每个 ID 天然唯一，所以它的 Base62 编码也唯一。没有冲突，不需要重试。6 个 Base62 字符可以表示约 560 亿个 URL。

补充：62 的来源是 0-9 数字 + a-z 小写字母 + A-Z 大写字母（10+26+26）。

**架构大致长这样 —**

客户端 -\> API 网关 -\> 两个服务 -\> 数据库。

短链服务负责写：生成 Base62 ID，把映射关系存进数据库。

2\. 跳转服务负责读：根据短 URL 查出长 URL 并返回。

**缓存与读扩展**

用 Redis，配合 LRU 淘汰策略。大约 20% 的 URL 承担了 80% 的流量——LRU 天然会把热点链接留在缓存里，把没人访问的淘汰掉。在此之上再设置一个 TTL。

对于缓存未命中的情况，用只读副本来分摊数据库的读压力。扩展的优先级是：先 Redis，其次只读副本，只有当写入压力也成为问题时才考虑数据库分片。不要一上来就分片。

数据库表结构大概会是这样：

urlId（该 URL 的唯一 ID）shortURL（缩短后的 URL）longURL（要跳转到的原始 URL）userID（创建该 URL 的用户）created\_at（创建时间）

这里用 SQL 就够了。查询都是简单的按键查找，没有复杂 join。规模极大时 Cassandra 也可行，但因为它不支持 join，你得把所有字段反范式化地放进同一张表。

[Bit.ly](https://x.com/Harry_The_Nerd/status/Bit.ly) 就讲到这里。

**设计 Pastebin**

**功能需求** 1. 粘贴一段文本，得到一个短链接 2. 拿到链接的人都能读到内容 3. 链接在一段时间后过期

**系统性质**

同样是读多写少，不是写多。一段 paste 创建一次，被读很多次。前面那套缓存方案在这里同样适用：用 Redis 加 LRU 淘汰来缓存高频访问的 paste。

与 [Bit.ly](https://x.com/Harry_The_Nerd/status/Bit.ly) 最关键的区别在于**内容存储**。

Pastebin 设计里最大的错误，是把文本 blob 直接存进数据库。大段文本内容会显著拖慢数据库。

所以我们把存储拆成两层：

1\. 数据库只存元数据：userID、shortLink、一个指向 S3 的 URL、created\_at、expires\_at。2. 对象存储（比如 AWS S3）存放真正的文本内容。

数据库里存的是指向内容的指针，而不是内容本身。这样能让数据库保持轻量和快速。

**架构**

客户端 -\> API 网关 -\> 两个服务 -\> 数据库 + S3。

1\. 写服务：接收文本，上传到 S3，生成 Base62 ID，把元数据和 S3 URL 存入数据库，这些在一次操作里完成。

2\. 读服务：接收短链接，从数据库取元数据，再从 S3 取内容，返回给用户。

**过期（这里很重要）**

表结构里一定要加 expires\_at，并且要提到有一个清理任务，把过期的 paste 从数据库和 S3 里一并删掉。这是 Pastebin 特有的细节，能体现你考虑的是真实的产品行为，而不只是理想路径。
