## 7 个重要的后端与分布式系统设计模式

现代后端系统早已不再是跑在一台机器上的单体应用。今天的应用要服务数百万用户、处理海量数据，并且在故障、流量高峰和网络抖动时依然保持可靠。要达到这种级别的可扩展性和韧性，工程师依赖的是那些经过验证的架构模式和分布式系统模式。Netflix、Amazon、Uber、Google、Meta 这些公司每天都在用它们。

本文介绍七个关键的后端与分布式系统模式：

**写回（Write-Behind / Write-Back）缓存**

**惊群问题（Thundering Herd）**

**分布式事务与两阶段提交（2PC）**

**物化视图模式**

**批量处理模式**

**读副本架构**

**全局限流**

## 1\. 写回（Write-Behind / Write-Back）缓存

**概述**

写回缓存模式先把写入暂存到一层快速缓存里，再异步落盘到数据库，以此提升写入性能。

也就是说，写操作不再每次都直接打到数据库，而是由应用先写入 Redis 或 Memcached 之类的缓存。稍后由后台 worker 分批把这些变更刷入数据库。

这样既减轻了数据库的写入压力，也降低了延迟。

工作流程：

客户端发出写请求。

数据立刻写入缓存。

用户很快收到成功响应。

后台 worker 定期把数据持久化到数据库。

在写入密集的系统里，数据库往往就是瓶颈。每个请求都同步写库，会拉高延迟并压垮数据库。

写回缓存的解法是：

- 减少数据库调用
- 把写入合并成批
- 缩短响应时间
- 更从容地扛住流量突增

**真实案例**

社交平台会用这套办法处理这类指标：

- 点赞数
- 观看次数
- 帖子曝光量
- 分析类计数器

比如 Instagram 并不会在每次有人看了一条 story 时就同步更新数据库，而是把计数累积在内存里，定期刷入。

**优点**

- 写入性能极快
- 数据库负载下降
- 吞吐量更高
- 批处理效率高

**缺点**

- 缓存在持久化之前崩溃会有丢数据的风险
- 只能做到最终一致性，而不是即时一致
- 需要配套的重试与恢复机制

**最佳适用场景**

- 分析系统
- 计数器与指标
- 日志系统
- 高频事件接入

## 2\. 惊群问题（Thundering Herd）

## 概述

惊群问题发生在缓存未命中或服务刚恢复时，大量客户端同时请求同一个资源。本来只需要一个请求去重建缓存，结果成千上万个请求同时打到后端，把数据库或服务压垮。

**场景示例**

设想一个电商应用，商品详情缓存 30 分钟。

缓存过期的那一刻：

- 成千上万用户请求同一个商品
- 所有请求都绕过缓存
- 每个请求都打到数据库
- 数据库 CPU 急剧飙升
- 系统延迟上升

这种请求洪峰就叫「惊群」。

**常见诱因**

- 缓存过期
- 服务重启
- 流量高峰
- 突发的重连风暴

**解决方案**

1\. 请求合并（Request Coalescing）：只放一个请求去重建缓存，其余的等待结果。

2\. 分布式锁：用 Redis 锁或 ZooKeeper 锁，确保只有一个进程执行昂贵的重算。

3\. 缓存过期时间随机化：避免所有缓存条目同时失效。

4\. Stale-While-Revalidate：先返回旧数据顶一阵，同时异步刷新缓存。

5\. 限流：保护下游系统不被打爆。

**真实案例**

Amazon 或 Flipkart 搞秒杀时，缓存失效如果处理不当，就会引发数据库流量的巨大脉冲。

妥善解决之后的收益

- 系统更稳定
- 数据库过载减少
- 用户体验更好
- 流量高峰期的可用性更高

## 3\. 分布式事务与两阶段提交（2PC）

**概述** 在分布式系统中，一笔业务事务可能牵涉多个服务和多个数据库。

例如：订单服务 + 支付服务 + 库存服务

如果一个服务成功、另一个失败，系统状态就可能不一致。

分布式事务通过保证所有参与方要么一起做到下面之一来解决这个问题：

- 一起成功提交
- 一起回滚

其中最广为人知的方案之一是两阶段提交（2PC）协议。

**两阶段提交如何工作**

阶段一：准备阶段

协调者询问所有参与者是否准备好提交。

每个参与者：

- 校验事务
- 锁定所需资源
- 回复 YES 或 NO

阶段二：提交阶段

如果所有参与者都回复 YES：

- 协调者下发 COMMIT
- 每个参与者永久应用变更

如果任何参与者回复 NO：

- 协调者下发 ROLLBACK
- 所有变更被撤销

## 示例

看一笔银行转账：

从账户 A 扣款

向账户 B 入账

这两个操作必须同时成功。

如果扣款成功而入账失败，钱就在系统里凭空消失了，这是不可接受的状态。

2PC 保证了跨分布式服务的原子性。

优点

- 强一致性
- 跨服务的原子事务
- 状态管理可靠

缺点

- 延迟高
- 存在阻塞行为
- 可扩展性受限
- 协调者会成为瓶颈
- 故障恢复场景棘手

现代替代方案

由于 2PC 代价高、速度慢，许多现代系统更倾向于：

- Saga 模式
- 事件驱动架构
- 补偿事务
- 最终一致性

**实际应用：** 传统银行系统和金融平台普遍使用分布式事务机制，因为一致性对它们至关重要。

## 4\. 物化视图模式

## 概述

物化视图是预先计算并存储下来的查询结果，用于优化昂贵的读操作。系统不再反复执行复杂的 join 和聚合，而是提前算好并存起来。这能显著提升读性能。

在大规模系统里，复杂的分析查询开销可能极大。

例如：

- 仪表盘分析
- 销售报表
- 用户统计
- 推荐结果汇总

实时跑这些查询会把数据库压垮。

**工作流程**

原始数据照常存储。

后台任务做聚合和加工。

预计算结果单独存放。

应用直接查询物化视图。

**真实案例：** YouTube 的分析仪表盘不会在每次页面加载时实时计算总观看量、观看时长和互动指标。

这些指标是定期聚合并存下来的。

**优点**

- 读取极快
- 查询复杂度下降
- 数据库 CPU 占用更低
- 仪表盘性能更好

**缺点**

- 数据可能过期
- 需要同步逻辑
- 额外的存储成本
- 刷新机制本身有复杂度

**常见刷新策略**

定时刷新

每隔几分钟或几小时刷新一次。

增量刷新

只更新发生变化的数据。

事件驱动刷新

一旦有事件发生就更新物化视图。

**最佳适用场景**

- 分析仪表盘
- 报表系统
- 推荐引擎
- 数据仓库

## 5\. 批量处理模式

## 概述

批量处理把多个小操作合并成更大的批次。系统不再逐个处理请求，而是把它们分组处理以提升效率。这个模式在分布式系统里用得非常多，因为网络调用、磁盘操作和数据库写入都很昂贵。

与其一行一行地插入 10000 条记录：

- 系统把记录分成批
- 一次性插入
- 减少网络开销
- 吞吐量大幅提升

每次数据库操作都有固定开销：

- 连接处理
- 磁盘同步
- 事务准备
- 网络延迟

批处理摊薄了这些重复成本。

**真实案例**

**邮件系统：** 群发邮件服务按批发送消息，而不是一封一封发。

**Kafka 消费者：** Kafka 消费者按批处理消息，把吞吐量拉满。

**支付系统：** 银行以批次为单位处理清算交易。

**优点**

- 吞吐量更高
- 基础设施成本更低
- 网络调用减少
- CPU 和磁盘利用率提升

**缺点**

- 单条数据的延迟变高
- 批次部分失败的处理复杂
- 重试更难做
- 需要调优批次大小

**最佳适用场景**

- ETL 流水线
- 数据接入系统
- 通知服务
- 日志系统
- 分析流水线

## 6\. 读副本架构

## 概述

随着应用增长，数据库的读流量往往远大于写流量。单台数据库服务器可能扛不住：

- 用户查询
- 搜索操作
- 仪表盘读取
- 分析请求

读副本通过创建主库的多份拷贝来解决这个问题。

## 架构

主数据库

负责：

- INSERT
- UPDATE
- DELETE

读副本

负责：

- SELECT 查询
- 报表
- 搜索操作
- 分析读取

数据从主数据库异步复制到各个副本。

**收益**

可扩展性提升

读流量被分散到多台服务器上。

主库负载下降

主库可以专注于写入。

可用性更好

某个副本挂了，其他副本继续服务。

查询性能更快

重量级读查询不再和写操作抢资源。

**挑战**

复制延迟

副本可能不会立刻反映最新的写入。

最终一致性

用户可能短暂看到旧数据。

故障转移复杂

宕机时提升副本为主库的流程可能很麻烦。

**真实案例**

社交平台常把读副本用于：

- 信息流生成
- 个人主页浏览
- 搜索功能
- 推荐系统

与此同时，写入依旧走主数据库。

**最佳适用场景**

- 读多写少的应用
- 分析系统
- 内容平台
- 大规模 API

## 7\. 全局限流

## 概述

限流控制的是一个用户或客户端在特定时间窗口内能发出多少请求。没有限流，系统就容易遭遇：

- 滥用
- DDoS 攻击
- 流量高峰
- 资源耗尽

在流量由多台应用服务器共同承接的分布式架构中，全局限流尤其重要。

**本地限流为什么不够：**

如果每台服务器各自独立统计请求数：

- 限额会不一致
- 用户可以通过打到不同服务器来绕过限制

全局限流用 Redis 之类的集中式存储来解决这一点。

**常见算法**

令牌桶：令牌以固定速率补充，请求消耗令牌。

漏桶：请求以恒定速率被处理。

滑动窗口：在一个移动的时间窗口内统计请求。

固定窗口计数器：更简单，但精度较差。

**真实案例**

API 网关

Stripe、Twitter 这类平台会限制 API 请求量。

登录系统

防止暴力破解。

支付系统

保护昂贵的金融操作。

AI 平台

控制使用成本，防止过载。

**优点**

- 保护基础设施
- 提升可靠性
- 防止滥用
- 实现资源的公平分配
- 有助于控制运营成本

**缺点**

- 额外的基础设施复杂度
- 限额设得不对会伤害用户体验
- 分布式同步有难度

**限流常用的工具：**

- Redis
- NGINX
- Envoy Proxy
- API 网关
- Cloudflare

这七个模式代表了现代后端工程中最实用、最广泛使用的一批技术。

每个模式都解决一类特定问题：

写回缓存：更快的写入 惊群问题：保护 + 流量高峰 + 稳定性 分布式事务：强一致性 物化视图：更快的读取 批量处理：更高的吞吐 读副本：读扩展能力 全局限流：系统保护

一旦你把这些模式吃透，思考问题的方式就会越来越像一名系统架构师。
