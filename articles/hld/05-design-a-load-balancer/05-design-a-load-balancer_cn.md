# 设计一个负载均衡器

> 负载均衡器如何工作，以及如何从零设计一个。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2046465659551576395](https://x.com/Harry_The_Nerd/status/2046465659551576395) · 2026-04-21

![封面图](https://pbs.twimg.com/media/HGYbxaVaoAAyiT1.jpg)

负载均衡器坐在用户和你的服务器之间，把进来的流量分发出去，让任何一台服务器都不会被压垮。在每秒 100 万请求的量级下（这是本设计的假设前提），设计得对不对，决定了系统是能扩展还是会崩溃。开始吧，各位大佬！

**功能需求** 1\. 把进来的流量分发到多台服务器（负载分发）2. 健康检查——发现并避开不健康的服务器 3. SSL 卸载——集中解密 HTTPS 流量 4. 粘性会话——始终把同一个用户路由到同一台服务器 5. 同时支持四层和七层流量 6. 配置系统——决定哪个服务器池用哪种算法

**四层 vs 七层**

不是所有负载均衡都一样。你工作在哪一层，决定了你能看到什么、能做什么：

**四层（传输层）**——只根据 IP 地址和 TCP/UDP 端口做路由，不看包内部的内容。快得飞起，适合那些不需要检查请求内容、只追求原始吞吐量的场景。

**七层（应用层）**——读取真实的 HTTP 请求，可以根据 URL 路径、请求头和 cookie 做路由。慢一些，但聪明得多：

/api -\> API 服务器池

/images -\> 图片服务器池

/checkout -\> 支付服务器池

大多数生产系统对应用流量用七层，其余的用四层。

单一入口——**VIP 与 DNS**

到了一定规模，你会跑多个负载均衡节点来做冗余。但客户端需要一个唯一的地址，你不能扔给他们三个 IP。万一其中一个挂了怎么办？

VIP（虚拟 IP）就是一个浮动的单一 IP，坐在所有负载均衡节点前面。如果节点 1 挂了，VIP 会自动漂移到节点 2。客户端毫无察觉，它们始终在跟同一个 IP 通信。

DNS 的做法类似：为同一个域名返回多个 IP 并轮换。更简单，但对生产系统来说，VIP 提供的故障转移更快、更可靠。

**五种负载均衡算法**

1\. 轮询（Round robin）

请求按顺序分发 -\> 服务器 1、服务器 2、服务器 3，再回到服务器 1。实现上就是 server = count % N，然后 count 自增。当所有服务器配置一致时，简单又有效。

2\. 加权轮询

和轮询一样，但每台服务器根据自身配置获得不同的权重。一台 32GB 内存、16 核的服务器权重高于 8GB、4 核的那台，它会按比例接收更多流量。当你的服务器集群是异构的（配置各不相同）时，这是正确的选择。

3\. IP 哈希

对客户端 IP 做哈希，再映射到某台服务器：server = hash(clientIP) % N。同一个客户端总是打到同一台服务器——不需要 Redis 就天然实现了粘性会话。缺点是：如果很多用户共享一个 IP（比如 NAT 后面的企业网络），分布会不均衡。另外，增删服务器时也会出问题。

4\. 一致性哈希

普通哈希在你增删服务器时会崩——N 变了，几乎每个请求都会被重新映射到另一台服务器。一致性哈希通过把服务器放到一个虚拟环上来解决这个问题：

环上位置（0 -\> 360）：

服务器 A -\> 90

服务器 B -\> 180

服务器 C -\> 270

某个请求哈希到位置 100

顺时针走 -\> 撞到位于 180 的服务器 B

\-\> 请求被路由到服务器 B

如果服务器 B 挂了，只有哈希落在 90 到 180 之间的请求会被重新映射到服务器 C，其他请求完全不受影响。重新映射的只有 1/N 的流量，而不是全部。这正是 Cassandra、Redis Cluster 和 CDN 都在用一致性哈希的原因。

5\. 最少连接数

把每个新请求路由到当前活跃连接数最少的服务器。当请求的处理时长差异巨大时，这种方式最理想：有些请求 10 毫秒就完了，有些要跑 10 秒。轮询会把长请求堆到倒霉的服务器上，而最少连接数天然能均衡真实负载。

**健康检查——主动与被动**

负载均衡器绝不能把流量发给一台已经死掉的服务器。两种互补的做法：

1\. 主动——负载均衡器每隔几秒向每台服务器发一次心跳请求。超时没响应 -\> 标记为不健康，立刻停止往那儿路由流量。

2\. 被动——负载均衡器观察真实流量。某台服务器返回了太多失败响应或超时 -\> 自动把它标记为不健康。

生产系统两种都用。主动能抓住彻底失联的服务器，被动能抓住那些活着但一直返回错误的服务器。

**SSL 卸载**

负载均衡器在边缘一次性解密 HTTPS 流量，然后以明文 HTTP 转发给后端服务器。你的服务器完全不用碰加密——由负载均衡器集中处理。SSL 证书放在负载均衡器上，而不是每台服务器上。这为整个集群省下了可观的 CPU。

**用 Redis 实现粘性会话**

粘性会话意味着用户总是落到同一台服务器上，这对有状态的应用至关重要。当你有多个负载均衡节点时，每个节点都得知道某个用户的会话在哪儿。

Redis 解决了这个问题。所有负载均衡节点都往同一个 Redis 集群读写会话映射：

用户 X -\> LB 节点 1 -\> Redis：「用户 X -\> 服务器 3」-\> 路由到服务器 3

用户 X -\> LB 节点 2 -\> Redis：「用户 X -\> 服务器 3」-\> 依然是服务器 3

**配置系统——Zookeeper**

一个中心化的配置存储定义了各种规则 -\> 哪个服务器池用哪种算法、权重怎么分配、健康检查间隔多久、SSL 证书放在哪里。Zookeeper 是这里的合适工具：负载均衡节点监听它的变更并实时自我更新，不需要重启。

**数据层**

负载均衡器是基础设施组件，不是数据密集型应用。它的存储需求关乎速度和协调，而不是业务数据的持久化：

Zookeeper —— 配置、算法规则、服务器权重

Redis —— 粘性会话 + 所有 LB 节点共享的服务器健康状态

InfluxDB / Prometheus —— 时序指标：每秒请求数、响应时间、错误率、流量分布。给 Grafana 这类监控面板提供数据。

不需要传统的 SQL 或 NoSQL 数据库——这也正是这个设计在架构上区别于大多数系统的地方。

**非功能需求**

可扩展性

在每秒 100 万请求下，单个负载均衡节点本身就是瓶颈。要在一个 VIP 后面水平部署多个 LB 节点，每个节点处理一部分流量。Redis 和 Zookeeper 让所有节点保持同步，使它们表现得像一个统一的系统。

延迟

负载均衡器位于每个请求的关键路径上。要让它保持轻量——算法决策在内存里完成，健康状态放在 Redis，配置从 Zookeeper 同步后缓存在本地。路由决策给每个请求增加的开销应该低于 1 毫秒。

可用性

VIP 后面挂多个 LB 节点，意味着没有单点故障。某个节点挂了，VIP 会立刻把流量漂到其他节点上。健康检查保证不健康的后端服务器被自动移出轮转。系统会优雅降级——是服务器变少，而不是一台都不剩。
