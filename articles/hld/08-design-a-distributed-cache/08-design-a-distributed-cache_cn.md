# 设计一个分布式缓存

> 分布式缓存层的架构。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2048052028174463278](https://x.com/Harry_The_Nerd/status/2048052028174463278) · 2026-04-25

![封面图](https://pbs.twimg.com/media/HGwfU3vbwAApUFQ.jpg)

缓存不是数据库，它是一层「加速层」。它挡在数据库前面，把热数据放在内存里，绝大多数请求根本不用碰磁盘就能返回。怎么设计一套能跑在几百个节点上的缓存，就是这篇拆解要讲的，各位。

**缓存 vs 分布式键值存储**

两者看着像，但目的根本不同：

分布式键值存储：永久存储，是数据的唯一真相来源，能撑住 TB 级数据，数据永远留着

分布式缓存：临时存储，是加速层，挡在数据库前面，数据会过期，只放热数据，全部装进内存

缓存里的数据永远是某份永久数据的副本。缓存挂了什么也不会丢，真正的数据一直在数据库里。

**功能需求**

put(key, value, TTL) -\> 带过期时间存入 get(key) -\> 返回值，或者缓存未命中 淘汰 -\> 缓存满了就按 LRU/LFU 清 失效 -\> 源数据更新时移除陈旧数据 未命中处理 -\> 从数据库取、存进缓存、再返回

**缓存写入策略**

发生缓存未命中、要去数据库取数据时，谁负责把它写回缓存？写操作又在什么时候进缓存？三种策略，各有各的权衡。

**旁路缓存（Cache Aside，懒加载）**

一切都由应用来处理。未命中时，应用自己去数据库取，再自己写进缓存。只有真正被请求的数据才进缓存，不浪费内存。但第一次请求总是慢的，而且缓存一挂，所有请求都会直接打到数据库。

get("user:123") -\> 缓存未命中 -\> 应用从数据库取 -\> 应用写入缓存 -\> 返回给用户

**写穿透（Write Through）**

每次写入同时落到缓存和数据库。缓存永远和数据库同步，绝不会有陈旧数据。代价是：每次写都更慢，而且缓存里会塞满可能永远读不到的数据。

put("user:123", "Rahul") -\> 写入缓存 -\> 同时写入数据库 -\> 两边都确认 -\> 成功

**写回（Write Behind / Write Back）**

只写缓存，数据库的写入稍后异步完成。写入快得飞起。危险的权衡是：如果异步写落盘之前缓存崩了，数据就永远没了。只有能接受一定数据丢失时才用它。

put("user:123", "Rahul") -\> 写入缓存 -\> 立刻返回成功 -\> 异步任务稍后写入数据库

经验法则：读多 -\> 旁路缓存。写多且需要一致性 -\> 写穿透。写多且速度优先于一致性 -\> 写回。

**跨节点分布——一致性哈希**

有了多个缓存节点，你得立刻知道某个键落在哪个节点上。一致性哈希把节点放在一个虚拟环上，每个键顺时针路由到最近的节点，也就是 O(1) 的查找；某个节点挂掉时，只有 1/N 的键需要重新映射。

**淘汰策略**

缓存节点的内存满了，总得清掉点东西。主要有两种策略：

LRU（Least Recently Used，最近最少使用）——淘汰最久没被访问过的数据。适合按「最近性」聚集的访问模式：社交媒体信息流、会话数据、最近搜索。

LFU（Least Frequently Used，最不经常使用）——淘汰累计访问次数最少的数据。适合按「热度」聚集的访问模式：YouTube 视频、Spotify 歌曲。热门内容即使最近没被访问也能留在缓存里。

像 Redis 这样的生产系统会两者结合：LFU 淘汰 + TTL 过期。这样既解决了频率问题，也解决了陈旧历史数据的问题。

**缓存失效——处理陈旧数据**

数据库更新后，缓存里还留着旧版本。有三种应对策略：

**TTL**

最简单的做法——让陈旧数据自然过期。给每个条目设一个 TTL。对那些能接受短暂陈旧窗口的非关键数据，这样就够了。

**事件驱动失效**

数据库发生变更时，往 Kafka 发一个事件。缓存消费这个事件，立刻删掉陈旧的键。几乎瞬时失效，没有陈旧窗口。适合关键数据。

用户更新资料 -\> 写数据库 -\> 向 Kafka 发布 "user:123 updated" -\> 缓存消费者删除 user:123 -\> 下一次读取从数据库取到新数据

**基于版本的失效**

每个缓存条目带一个与数据库对应的版本号。每次读取时比对版本，不一致就说明是陈旧的，去取新的。精确，但需要在数据库表结构里维护版本。

冷启动——节点重启时会发生什么

缓存数据活在内存里，一次重启就全没了。这完全没问题。请求进来时缓存会自然预热，每次未命中都从数据库回填一次。这段冷启动期，是换取缓存带来的速度收益所接受的代价。

**数据层**

分布式缓存本身没有持久化数据库。它是加速层，不是存储层：

1\. 每个节点上的内存保存 key、value、TTL 和版本。重启即丢，无所谓。

2\. Zookeeper 保存哈希环配置、节点健康状态（由 gossip 协议提供）、淘汰策略、TTL 默认值、每个节点的缓存容量上限。

3\. Kafka——用于失效的事件流。数据库发布变更事件，缓存消费者删掉陈旧的键。

完整架构

客户端 ↓ 应用服务器 ↓ 缓存集群（一致性哈希 → 对应节点）↓ 缓存命中 → 微秒级立刻返回值 缓存未命中 → 从数据库取 → 带 TTL 存入缓存 → 返回给客户端 后台：Kafka → 数据库更新时的失效事件 Gossip → 节点健康检测 Zookeeper → 环配置、淘汰策略、TTL 默认值

**非功能需求**

**延迟**

一切都在内存里。缓存命中在微秒级返回。一致性哈希让路由决策是 O(1) 的。目标是每次缓存命中都做到亚毫秒响应，把数据库负载压到最低。

**可扩展性**

往一致性哈希环上加节点即可。键会自动重新分布，且重映射量极小。每个节点相互独立，读写都不需要跨节点协调。水平扩展的开销几乎为零。

**可用性**

某个缓存节点挂了，请求回落到数据库，慢一些但仍然可用。gossip 协议在几秒内发现故障，Zookeeper 更新环配置，流量自动重新路由。系统是优雅降级，而不是彻底不可用。
