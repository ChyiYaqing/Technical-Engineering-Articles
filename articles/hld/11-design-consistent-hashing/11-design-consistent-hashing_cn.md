## 分布式系统里的哈希是什么？

任何分布式系统里都有缓存集群、数据库分片、负载均衡器，而我们需要一种办法来决定：这个 key 该由哪个节点负责？最简单的答案是取模哈希。

给定一个 key k 和 N 台服务器，我们计算：

**node = hash(k) mod N**

它确定、快速、易于实现。每个客户端都能独立算出正确的节点，不需要任何协调。这套方案一直很好用——直到服务器数量发生变化。麻烦就是从这里开始的。

**重新哈希（Rehashing）问题**

假设你有 4 台服务器和一个繁忙的缓存。每个 key 通过 hash(k) mod 4 映射到某台服务器。现在为了分担负载，你加了第 5 台服务器。公式变成了 hash(k) mod 5。

**几乎每一个缓存的 key 都会被重新映射到另一台服务器上。** 一个存着上百万条目的缓存瞬间全部失效。所有流量穿透到数据库，形成惊群，足以把整个系统拖垮。

数学上是这样的：

![](https://pbs.twimg.com/media/HIxGRxwbUAEkmuz.jpg)

服务器宕机时会发生同样的灾难。N 减一，一切重新映射，之前所有命中缓存的查询此刻同时打到冷存储上。

在分布式系统里，服务器故障不可避免。把服务器数量当作常量的哈希方案，在规模上来之后就是个隐患。

**一致性哈希：核心思路**

一致性哈希正是为解决这个问题而生的。它的洞见是：不用取模把 key 映射到服务器，而是把 key 和服务器都映射到同一个抽象的环上——一条从 0 到 2³²−1、首尾相接的数轴。

**放置：** 每台服务器按其 IP、主机名或 ID 做哈希，得到环上的一个位置。每个 key 同样哈希得到自己的位置。

**查找：** 要找出负责某个 key 的服务器，从该 key 的位置沿顺时针方向走，遇到的第一个服务器节点就是它的归属。

key\_position = hash(key) server\_node = 从 key\_position 顺时针方向的第一台服务器

查找可以用有序数组或平衡二叉搜索树高效实现，一次二分查找就能在 O(log N) 时间内定位到正确的服务器。

![](https://pbs.twimg.com/media/HIxGtRybMAAiQyW.png)

**一致性哈希如何解决重新哈希问题**

当增删一台服务器时，只有受影响那段弧上的 key 需要迁移。其他服务器完全不受影响。

**新增服务器 S5：** S5 被放到环上的某个位置。只有 S5 的前驱（逆时针方向）到 S5 之间的那些 key 现在归属 S5，其余的原地不动。

**移除 S2：** S2 的 key 迁移到 S3（顺时针方向的下一个节点）。别的服务器毫发无损。

在 N 台服务器、总共 K 个 key 的情况下，任何一次变更只需重新映射 K/N 个 key。相比取模哈希那种近乎全量的重新映射，这是巨大的改进。

取模哈希 -\> 全部 key 的约 (N−1)/N

一致性哈希 -\> 约 K/N（仅一段弧）（更优）

**基础一致性哈希的问题**

基础的一致性哈希解决了重新哈希问题，却引入了一个新问题：**分布不均匀**。

服务器按名字或 IP 哈希放到环上时，并不能保证它们均匀分布。实践中你常会遇到：

**弧长不均。** 一台服务器可能占了环的 50%，另一台只占 5%。占大弧的那台承担 10 倍流量，成为热点，其他的大部分时间闲着。

**级联故障。** 如果一台重载的服务器宕机，它的所有 key 会顺时针挪到下一个节点。而那个节点本来就在处理自己那份流量，现在负载翻倍甚至翻三倍，很可能跟着挂掉。

**无法支持异构硬件。** 内存和 CPU 是同伴两倍的服务器，理应承担两倍的 key。基础一致性哈希对此没有任何机制，不管容量多大，每台服务器分到的弧长都差不多。

这些不是边缘情况，而是把少量节点用哈希函数丢到环上必然会出现的结果。

**虚拟节点：解法**

解法很优雅：不再让每台物理服务器在环上只出现一次，而是用不同的哈希输入把它放置多次。这些位置叫做**虚拟节点**（vnode）。

对于配置了 3 个 vnode 的服务器 S1，你分别哈希 "S1#1"、"S1#2"、"S1#3"，把这三个位置都放到环上。落在其中任一位置附近的 key，都由同一台物理机 S1 来服务。

当 vnode 足够多时（通常每台物理服务器 100 到 200 个），每台服务器的位置就会均匀散布在整个环上。结果是——哪怕物理服务器数量很少，各自占据的弧长总和也大致相等。

```python
for each server S:
    for i in range(VNODE_COUNT):
        position = hash(f"{S}#{i}")
        ring.add(position, server=S)
```

**虚拟节点带来的能力：**

- **接近均匀的负载分布。** 每台物理服务器最终拥有许多零散的小弧，平均下来总占比大致相等。
- **优雅降级。** 一台服务器故障时，它那约 150 个 vnode 位置分散在环的各处。接手它 key 的相邻服务器很可能分属许多不同的物理机，于是额外负载被摊薄，而不是全砸到某一个邻居身上。
- **按容量按比例分配。** 给性能更强的服务器分配更多 vnode，它就会按比例承担更多负载。容量是别人两倍的服务器拿到两倍的 vnode，自然就处理约两倍的 key。
- **更平滑的扩容。** 新服务器带着大量 vnode 加入时，它是从许多现有服务器那里各拿走一小段弧，而不是从某个邻居手里整块夺走一大段，从而降低了对整个集群的扰动。

**你会在哪些真实系统里见到它**

带虚拟节点的一致性哈希是好几个广泛使用的系统的骨架：

**Amazon DynamoDB 和 Apache Cassandra** 用 vnode 在集群中做数据分区。Cassandra 的 token ring 就是这套设计的直接实现。

**内容分发网络（CDN）** 用一致性哈希把请求确定性地路由到边缘节点，不需要中心化的查找表。

**负载均衡器** 用它来维持会话粘性（sticky session），在后端实例扩缩容时把扰动降到最低。

演进路径是：取模哈希 -\> 一致性哈希 -\> 虚拟节点。这是分布式系统设计在实践中如何推进的经典范例：每个方案在当下都干净、够用，直到规模暴露了它的假设，然后下一个方案被造出来，专门针对那种失效模式。
