# 设计 Spotify

> 类 Spotify 音乐流媒体平台的系统设计。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2063952850531897396](https://x.com/Harry_The_Nerd/status/2063952850531897396) · 2026-06-08

![封面图](https://pbs.twimg.com/media/HKOlcAkbcAA8RYN.jpg)

## 1\. 需求

**功能性需求**

- 搜索歌曲、艺人、专辑和歌单
- 以自适应音质播放歌曲
- 歌单管理：创建、查看、更新、删除和分享
- 由机器学习流水线驱动的歌曲推荐

**非功能性需求**

- 高可用：部分组件故障时，音频分发要优雅降级，而不是整体不可用
- 低延迟播放：点击播放后，第一个音频分片必须在毫秒级开始播放
- 巨大的读吞吐量：每个服务的读写比例都严重偏向读
- 容错：任何单点故障都不应让核心播放功能瘫痪
- 推荐、搜索索引这类非关键路径可以接受最终一致性

## 2\. 容量估算

- **日活用户：** 2 亿
- **每日播放次数：** 10 亿
- **单曲平均大小：** 5 MB
- **每天消耗的数据总量：** 5 MB \* 10 亿 = 约 1 PB/天（便于估算的取整值）

这是原始消费量，但并不是基础设施真正需要从源站提供的量。假设 CDN 命中率约为 80%，只有 20% 的请求会打到源站，源站的量因此降到大约 **200 TB/天**，这就好办多了。

这个估算立刻告诉我们三件事。第一，CDN 是**不可妥协的**，没有它源站的基础设施成本会高得离谱。第二，缓存必须在整个技术栈的每一层都做得很激进，而不只是在边缘。第三，由于读写比例极度失衡，整个系统都应该为读性能做优化，写路径则可以承受稍高一点的延迟。

## 3\. API 网关

所有客户端请求——不管来自手机 App、桌面客户端、网页浏览器还是智能电视——都通过 API 网关进入系统。它的职责是：

- **认证与授权：** 在请求到达任何下游服务之前校验 token
- **限流：** 防止滥用，保护下游服务不被流量高峰冲垮
- **请求路由：** 把请求分发到正确的微服务
- **协议转换：** 把不同类型客户端的请求归一化

一个关键的设计决策是明确 API 网关不该做什么。它绝不能出现在重处理的链路上。具体来说，音频上传和转码流水线必须完全绕开它。让几百兆的音频文件穿过 API 网关会让它变成严重的瓶颈，还会引入不必要的延迟。网关的定位是处理轻量、快路径的请求，而不是搬运大块二进制负载数据。

## 4\. 上传与转码流水线

这是系统中最复杂的写路径。当唱片公司或艺人上传一首新曲目时，会发生下面这些步骤。

**第 1 步：直传到转码服务**

原始音频文件被直接发送到转码服务，完全绕开 API 网关。这是刻意为之：文件很大，处理很吃 CPU，这两个特性都不该放在请求路由器后面。

**第 2 步：转码**

转码服务负责三件事：

**音质变体。** 原始文件被编码成多个码率的版本。通常是极低带宽下的 96kbps、普通的 128kbps、高音质的 256kbps 和会员的 320kbps。正是这一点让 Spotify 能在用户网络变差时无缝降低音质而不打断播放。

**分片。** 每个音质变体都被切成一段段约 2-10 秒的小片段。这些分片是彼此独立、无状态的 HTTP 对象。这一点是整个流媒体架构的基础：它让 CDN 缓存成为可能，让用户可以跳到歌曲任意位置而无需下载此前的全部内容，也让客户端只要换一个分片 URL 就能在播放途中切换音质变体。

**DRM 认证。** 每个分片都被加密，并绑定到一份只有通过认证的付费用户才能获取的许可证。这保护了艺人和唱片公司的知识产权。

**第 3 步：存入 S3**

处理好的分片（涵盖所有音质变体）存进对象存储（S3 或同类产品）。对象存储在这里是正确选择，因为音频分片体积大、不可变、从不原地更新。分片一旦写入就再也不会改变。S3 提供了持久性、近乎无限的存储空间，以及与 CDN 分发的原生集成。

**第 4 步：向 Kafka 发布事件**

转码完成后，转码服务向一个 Kafka topic（比如叫 song.transcoded）发布一条事件，包含歌曲 ID 和相关元数据。转码服务并不关心接下来会发生什么，它不会直接调用元数据服务或搜索服务。这种解耦是刻意的，也是关键的。

**第 5 步：通过 Kafka 消费者扇出**

有两个彼此独立的消费者订阅 song.transcoded topic：

**元数据 Worker：** 读取事件，把歌曲元数据（标题、艺人、专辑、流派、时长、分片清单 URL）写入元数据数据库，然后更新元数据缓存。

**搜索索引 Worker：** 读取同一条事件，把歌曲索引进 Elasticsearch，让它在几秒内就能被搜到。

这就是事件驱动的扇出模式。两个消费者互不阻塞。如果搜索索引 Worker 临时挂掉，它只是在 Kafka offset 上落后一段，恢复后会追上来，不会丢数据。这是让多个数据存储保持最终一致、同时又不让服务之间紧耦合的正确做法。

**这条流水线里的瓶颈**

转码这一步本身就是主要瓶颈。把一首曲目编码成五种音质变体、给每个变体分片、再施加 DRM，都非常吃 CPU，长曲目可能要花上几分钟。应对办法是把转码服务做成可水平扩展的 worker 池，让很多 worker 从队列里拉取任务。单个转码任务彼此独立，所以能线性扩展。下游的 Kafka 层在这个量级上没有实质瓶颈，因为它生来就是干这种高吞吐事件流的活。

## 5\. 播放服务

播放是整个系统中读最重、对延迟最敏感的路径。当用户点击播放时：

**第 1 步：请求元数据和签名 URL**

客户端通过 API 网关向播放服务发送 GET /songs/{id}。播放服务做两件事：从元数据服务取出歌曲元数据（标题、艺人、专辑封面、时长），以及生成一个指向 S3/CDN 上 HLS 清单文件的**签名 URL**。签名 URL 的存活时间（TTL）很短，并且与已认证的用户绑定，这就是 DRM 在分发层的执行方式。

**第 2 步：HLS 清单**

客户端拉取 HLS 清单文件，这是一个小小的文本文件，列出所有可用的音质变体，以及每个变体下每个分片的 URL。清单本身也是一个可被 CDN 缓存的对象。

**第 3 步：拉取分片**

客户端开始按顺序拉取分片。每个分片请求形如 GET /songs/{song\_id}/{quality}/{chunk\_index}.ts。这些请求打到离用户最近的 CDN 边缘节点。缓存命中时（热门歌曲大约 80% 的情况如此），CDN 直接返回分片，后端完全不参与。未命中时，CDN 从 S3 取回分片、缓存下来再返回。

**HLS 是正确的协议选择**

HLS（HTTP Live Streaming）正是为这种场景设计的。它完全跑在标准 HTTP 之上，意味着每个分片都是一次普通的 HTTP GET，CDN 天然就能处理。分片是 URL 确定的静态对象，因此完美可缓存。客户端在本地通过切换请求哪个变体的分片来控制音质自适应，服务端不需要知道也不必关心。正是这种简单性让架构如此有韧性：会话一旦开始，播放路径在服务端几乎没有任何状态。

**天然的韧性**

由于分片在 CDN 边缘各自独立缓存，即便元数据服务、播放服务甚至源站 S3 桶临时不可达，正在播放中的用户仍然能继续收到音频——分片就在 CDN 上。这是架构自然涌现出的韧性，并不需要专门的故障转移逻辑。这也是为什么 Spotify 在网络变差、连不上自己后端时仍然能继续放歌。

**播放路径的瓶颈**

CDN 吸收了 80% 的负载，所以真正的瓶颈是那 20% 未命中缓存、要打到 S3 的请求。S3 高可用且持久，但在缓存未命中时会增加延迟。对于刚上传、从没被请求过的新歌，第一个听众会触发一次缓存填充，这就是所谓的冷启动，会让第一次请求的延迟稍高一些。对上传场景来说这通常可以接受，但值得留意。播放服务本身只签发签名 URL 和取元数据，是无状态、可水平扩展的，没有实质瓶颈。

## 6\. 搜索服务

搜索的读模式和播放截然不同。用户输入一个不完整的字符串，就期望在毫秒之内拿到跨歌曲、艺人、专辑和歌单的、排好序的模糊匹配结果。

**存储引擎 - Elasticsearch**

Elasticsearch 是解决这个问题的正确工具。它构建在倒排索引之上，让全文搜索、部分匹配和相关性排序都极快。它能处理：

- **前缀与模糊匹配-** 输入 "Tay" 返回 Taylor Swift，输入 "Bohemn" 返回 Bohemian Rhapsody
- **多实体搜索-** 一次查询同时搜索歌曲、艺人、专辑和歌单
- **相关性排序-** 结果按文本匹配得分、热度信号和个性化因素的组合来排序

Elasticsearch 不作为记录系统使用。它是从元数据数据库派生出来的搜索索引。任何歌曲元数据的唯一真实来源都在元数据数据库里，Elasticsearch 只是这份数据的一个面向读优化的投影。

**保持 Elasticsearch 同步**

这时上传流水线里那套 Kafka 扇出就派上用场了。搜索索引 Worker 订阅 song.transcoded topic，为每一次新上传写入 Elasticsearch。至于更新，比如某位艺人改了名字：元数据服务会往另一个 Kafka topic 发布更新事件，搜索索引 Worker 同样消费这个 topic。这样就能让 Elasticsearch 与唯一真实来源保持最终一致，而不引入任何同步耦合。

**缓存热门搜索结果**

对于极其常见的查询——搜 "Drake"、"Taylor Swift"、"workout playlist"——结果会以较短的 TTL 缓存在 Redis 中。这能避免 Elasticsearch 每秒被成千上万条一模一样的查询轰炸。

**搜索的瓶颈**

在极端查询量下，Elasticsearch 集群可能成为瓶颈，尤其是开了模糊匹配的复杂多字段查询。缓解手段是组合拳：用 Redis 缓存热门查询（在流量打到 Elasticsearch 之前就滤掉绝大部分重复请求）、水平扩展 Elasticsearch 集群，以及查询优化——针对音乐搜索的具体访问模式去调整分析器和索引映射。

## 7\. 元数据服务

元数据服务是歌曲、艺人、专辑和歌单所有描述性数据的唯一真实来源。它也是系统中被依赖最广的服务：搜索、播放、歌单和推荐都要从它这里读数据。

**数据库 - PostgreSQL（分片）**

歌曲元数据有清晰的关系结构。一首歌属于一张专辑，一张专辑属于一位艺人，一位艺人有很多歌，一首歌有多个流派。PostgreSQL 天然能处理这些关系，还提供强一致性保证——这一点在这里很重要：当一首新歌被索引进 Elasticsearch 时，它索引的元数据必须和元数据数据库里的一致。

在 Spotify 的量级上，单个 PostgreSQL 实例扛不住读负载。数据库要做水平分片，通常按艺人 ID 或歌曲 ID 分，每个分片再配多个只读副本。绝大多数元数据读请求走只读副本，写请求走主节点。

**缓存 - Redis**

元数据数据库前面挡着一层 Redis 缓存，吸收掉绝大部分读流量。热门元数据（当红艺人、热门歌曲、榜单专辑）的缓存命中率非常高，因为同样的记录每天要被请求上百万次。缓存失效发生在元数据 Worker 处理来自 Kafka 的上传事件或更新事件时。

**元数据层的瓶颈**

元数据服务是系统中两大关键瓶颈之一，另一个是 CDN。有三个主要服务依赖它。没有 Redis，PostgreSQL 的只读副本会被压垮；没有分片，单个数据库实例会成为吞吐量的硬天花板。正是 Redis 缓存、只读副本和水平分片这三者的组合，让这一层能够扩展。剩下的风险是缓存击穿：如果 Redis 挂了，所有服务会同时回落到数据库。这要靠熔断器和错开的 TTL 来缓解。

## 8\. 歌单服务

歌单是一个兼具社交和个人属性的功能。用户创建歌单、打理歌单、分享给朋友，有时还会协作编辑。数据模型很直白：一个用户有很多歌单，一个歌单有很多歌（用歌曲 ID 引用），一个歌单可以分享给其他用户。

**访问模式**

歌单的访问模式简单且基于键：

- 取某个用户的全部歌单 —— 按用户 ID 查
- 取某个歌单的全部歌曲 —— 按歌单 ID 查
- 添加或移除一首歌 —— 按歌单 ID 写
- 分享歌单 —— 把另一个用户 ID 与某个歌单 ID 关联起来

读的时候不需要任何复杂 join。当客户端需要歌曲详情（标题、艺人、时长）时，它会拿歌单里存的歌曲 ID 单独去元数据服务取。歌单服务本身只存储和返回 ID。

**数据库 - Cassandra**

考虑到访问模式简单、基于键，写入量大（用户不停地改歌单），还要扩展到全球数十亿个歌单，这里 Cassandra 比 PostgreSQL 更合适。

Cassandra 是一种宽列存储，为高写入吞吐和水平扩展做了优化。它不支持 join，但这没关系，因为我们本来就不需要——歌曲元数据是单独取的。它的分区键模型直接对应上述访问模式：按用户 ID 分区就能取到该用户的全部歌单，按歌单 ID 分区就能取到该歌单的全部歌曲。

Cassandra 的复制因子（通常是跨多个可用区的 3 副本）确保即使有节点宕机，歌单的读写也能不中断地继续。相比单主的关系型数据库，这是一个显著的韧性优势。

**歌单服务的瓶颈**

Cassandra 最主要的隐患是热分区。如果某个极其热门的共享歌单（比如一个有数百万关注者的 Spotify 官方编辑歌单）被持续访问，它所在的分区会承受不成比例的流量。缓解办法是把热门歌单缓存在 Redis 里，这样热门歌单的绝大多数读请求根本不会走到 Cassandra。

## 9\. 推荐服务

机器学习模型本身不在讨论范围内，但给它喂数据的基础设施在。推荐的质量上限，取决于它所依赖的行为信号。

采集的信号

- **播放事件-** 播了哪首歌、播了多久、是否很早就被跳过
- **加入歌单-** 用户主动选择收藏了哪些歌
- **搜索模式-** 用户反复搜索哪些艺人和流派
- **流派分布-** 用户收听历史中各流派的占比
- **协同过滤信号-** 听过歌曲 X 的用户也听了歌曲 Y

**采集架构**

每一次用户交互都会产生一条事件。每天 10 亿次播放，再加上跳过、搜索和歌单修改，这是一条量级极大的写路径。把这些事件同步写进数据库会是灾难性的，它会制造写瓶颈，拖垮用户体验。

正确做法是：每一次客户端交互都往 Kafka 发布一条事件。Worker 从 Kafka 消费，写入分析存储（Cassandra 或 ClickHouse 都很合适，两者都能高效处理高写入量和时序类数据）。机器学习流水线按固定周期（每小时或每天）从分析存储读数据，重新计算推荐结果，再把结果以用户 ID 为键写回 Redis。

**推荐结果的服务下发**

给用户下发一条推荐只需要一次 Redis 读取 —— GET recommendations:{user\_id}，这是整个系统里成本最低的操作之一。所有重活都在离线的机器学习流水线里干完了，而不是在请求时刻。

**推荐服务的瓶颈**

瓶颈不在下发推荐，而在采集流水线。Kafka 必须扛住所有日活用户同时产生的全部事件量。这仍在 Kafka 的设计能力范围之内，它本来就是为这个量级而生的。更微妙的隐患是分析存储的写吞吐，这正是这一层选 ClickHouse 或 Cassandra（而不是 PostgreSQL）的原因。

## 10\. 完整数据流汇总

**上传流程：** 唱片公司 -\> 转码服务 -\> S3（分片，所有音质变体） -\> Kafka（song.transcoded 事件） -\> 元数据 Worker -\> 元数据数据库 + Redis 缓存 -\> 搜索 Worker -\> Elasticsearch **播放流程：** 客户端 -\> API 网关 -\> 播放服务 -\> 签名 URL + 元数据 客户端 -\> CDN 边缘节点（缓存命中约 80%） -\> 直接返回音频分片 客户端 -\> CDN 边缘节点（缓存未命中约 20%） -\> S3 -\> CDN 缓存 -\> 返回音频分片 **搜索流程：** 客户端 -\> API 网关 -\> 搜索服务 -\> Redis（热门查询缓存） -\> Elasticsearch（缓存未命中时） -\> 元数据服务（为结果补全完整元数据） **歌单流程：** 客户端 -\> API 网关 -\> 歌单服务 -\> Cassandra（歌单结构） -\> 元数据服务（按 ID 取每首歌的详情） **事件采集流程：** 客户端交互 -\> Kafka -\> 分析 Worker -\> 分析数据库 -\> 机器学习流水线（周期性） -\> Redis（推荐结果）

## 11\. 韧性与容错

**CDN + HLS 分片**是系统中最重要的韧性来源。由于音频分片在边缘节点各自独立缓存、并通过普通 HTTP 分发，即便元数据服务、播放服务或源站 S3 临时不可达，正在播放中的用户仍然能继续收到音频。这不需要任何专门的故障转移逻辑，是架构的自然结果。

**Kafka 解耦**意味着上传流水线的各个组件可以独立地故障和恢复。如果搜索索引 Worker 挂了一小时，它只是在自己的 Kafka offset 上落后，恢复后追上来即可，一条事件也不会丢。转码服务和元数据 Worker 完全不受影响。

**Cassandra 复制**采用跨可用区的 3 副本复制因子，确保歌单数据能扛住节点和可用区级别的故障。Cassandra 的可调一致性让歌单服务可以按操作类型在强一致性（所有副本必须达成一致）和最终一致性（最快的可用副本响应）之间做选择。

**多层 Redis 缓存**降低了高负载下对主数据存储的依赖。即使元数据数据库的只读副本变慢，Redis 仍然吸收了大部分流量。熔断器则防止缓存故障级联成数据库彻底过载。

**元数据数据库的只读副本**确保系统中被依赖最广的数据存储在读路径上没有单点故障。写走主节点，读扇出到各个副本。

## 12\. 技术选型汇总

**API 网关** -\> Kong / AWS API Gateway（认证、限流、路由）

**对象存储** -\> AWS S3（不可变的音频分片，持久，与 CDN 原生集成）

**CDN** -\> CloudFront / Akamai 边缘节点（缓存，吸收 80% 的播放负载）

**播放协议** -\> HLS（分片、自适应码率、对 CDN 友好、无状态）

**解耦** -\> Apache Kafka（高吞吐事件扇出，持久，可回放）

**搜索引擎** -\> Elasticsearch（全文、模糊匹配、相关性排序）

**元数据数据库** -\> PostgreSQL（分片 + 副本）（关系结构，强一致性）

**歌单数据库** \-\> Cassandra（基于键的访问，高写入吞吐，水平扩展）

**缓存** -\> Redis（热门元数据、推荐结果、搜索结果、歌单热点读）

**分析存储** \-\> Cassandra / ClickHouse（高写入量，时序数据，机器学习流水线的输入）
