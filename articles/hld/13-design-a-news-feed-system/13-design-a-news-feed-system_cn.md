# 设计一个信息流系统

> 一个可扩展信息流的系统设计。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2058553384735842654](https://x.com/Harry_The_Nerd/status/2058553384735842654) · 2026-05-24

![封面图](https://pbs.twimg.com/media/HJFtHJ-bIAAmbIa.jpg)

## 问题描述

设计一个类似 Facebook 或 Inshorts 的信息流系统：用户可以发布内容，并看到一份来自其关注对象、按时间排序的个性化信息流。

## **需求与范围**

**功能需求：**

- 用户可以创建帖子：POST /api/v1/newPost
- 用户可以拉取自己的信息流：GET /api/v1/posts
- 信息流按时间顺序排列

**非功能需求：**

- 1000 万日活用户（DAU）
- 信息流读取要高可用、低延迟
- 信息流投递可以接受最终一致性

**粗略估算**

DAU - 1000 万 读写比 - 10 : 1 平均帖子大小 - 200 KB（含图片 URL） 写吞吐 - 60 次写入/秒 读吞吐 - 580 次读取/秒 每日新增数据 - 600 GB/天 每秒服务的读数据量 - 2.3 GB/秒

如此高的读吞吐意味着**缓存没得商量**。

**核心设计决策**

**写扩散与读扩散（混合模型）**

**写扩散（Push 模型）**

用户 A 发帖时，你立刻把这条帖子推送到 A 的所有关注者的信息流里。如果 A 有 1000 个关注者，就在写入时把这条帖子写进 1000 个用户预构建的信息流缓存中。

**结果：** 关注者打开信息流时内容已经就绪，直接读缓存即可，读取极快。

**问题：** 如果一个拥有 1 亿关注者的名人发帖呢？**几秒内 1 亿次缓存写入。** 这就是所谓的**热点键 / 名人问题**。

**读扩散（Pull 模型）**

用户打开信息流时，才去拉取他关注的所有人的帖子，当场组装出信息流。

**结果：** 读取更慢，因为是实时计算出来的，但写入很便宜。

**问题：** 580 次读取/秒，每次读取可能要查 500 个关注对象，这意味着**每个请求都带来巨大的数据库扇出**。

**折中点（混合模型）**

Facebook / Twitter 这类真实系统大多采用**混合方案：**

- **普通用户** -\> 写扩散
- **名人 / 高关注量账号** -\> 读扩散

## **按时间排序**

信息流以有序集合（sorted set）的形式存在 Redis 里，键为 UserFeed:{userId}，以时间戳作为分值。对一个以新闻为主的产品来说，不需要排序算法。

## **写路径**

客户端调用 POST /api/v1/newPost -\> 打到 API 网关

网关路由到 Post 服务，该服务把帖子写入 Post DB（NoSQL）和 Post Cache（Redis）

Post 服务向 Kafka 发布一个事件

扩散 worker 异步消费 Kafka：查询图数据库拿到作者的所有关注者；对每个关注者，把新的 postId 推入其 Redis 信息流有序集合

通知服务同样消费 Kafka，并发送推送提醒

## **读路径**

客户端调用 GET /api/v1/posts -\> 打到 API 网关

网关路由到 Get 服务

Get 服务从 Feed Cache（Redis）取出该用户预构建的信息流，即一串 postId

缓存命中时：用 Post Cache 里的完整帖子内容把每个 postId 填充完整

缓存未命中时：回退到 Post DB，并回填缓存

## **数据库选型**

Post DB - NoSQL（例如 Cassandra）- 高写吞吐，schema 灵活

图数据库 - Neo4j / 邻接表 - 高效遍历关注/被关注关系

Feed Cache - Redis 有序集合 - O(log n) 插入，读取即得排序结果

Post Cache - Redis - 低延迟的帖子内容填充

**媒体走 CDN**

在 2.3 GB/秒 的读吞吐下，直接从 Post DB 提供图片和视频将是灾难性的。所有媒体资源存放在对象存储（例如 S3）中，通过 CloudFront 这样的 CDN 分发。数据库里的帖子记录只保存媒体 URL，而不是二进制内容本身。Cache-Control 响应头确保图片从离用户最近的边缘节点返回，大幅降低源站负载和延迟。

**负载均衡**

API 网关与每个下游微服务之间都有一层负载均衡器——Post 服务、Get 服务、扩散 worker 和通知服务。这样任何单个实例都不会成为瓶颈，也让水平扩展成为可能。负载均衡层的健康检查会透明地处理实例故障。

**信息流分页**

GET /api/v1/posts 接口不可能在一次响应里返回所有帖子。这里用的是基于游标的分页，而不是基于偏移量的分页，因为信息流一大，偏移量的代价就上来了。每次响应返回一个 nextCursor（本次最后一条帖子的时间戳）。下次请求带上这个游标，Get 服务就从该分值开始，从 Redis 取出接下来的 N 个 postId。无论信息流多大，分页都保持 O(log n)。

**Kafka 的可扩展性**

Kafka 主题按帖子作者的 userId 分区。这保证同一用户的所有事件落在同一分区上，从而保持顺序。扩散 worker 的 Pod 属于同一个消费者组，每个 Pod 拥有一个或多个分区，随写吞吐增长而水平扩展。系统扩容时可以在不停机的情况下增加分区数。

**Redis 中的数据保留**

Redis 内存是有限的。每个用户的信息流有序集合最多保留最近 1000 个 postId。扩散 worker 推入新的 postId 时，会执行 ZREMRANGEBYRANK 裁掉超出上限的条目。请求更早的帖子会穿透到 Post DB，它是完整历史信息流的事实来源。

**认证与限流**

认证在 API 网关层用 JWT token 完成。每个请求在到达任何下游服务之前都会先被校验。限流同样在网关强制执行：POST /api/v1/newPost 这类写接口按用户维度限速，以防滥用并保护 Kafka 不被写入尖峰冲击。读接口的额度更宽松，但依然有上限，以保护 Get 服务。

**搜索**

信息流读取和发帖不承担搜索职责。为此单独维护一个 **Elasticsearch** 集群。每当一条帖子写入 Post DB，一条变更数据捕获（CDC）管道就异步把它同步到 Elasticsearch。用户搜索帖子、话题或关键词时，打到的是由 Elasticsearch 支撑的独立搜索服务，与信息流读路径完全解耦。

## **瓶颈与权衡**

**名人问题**：如果一个用户有数百万关注者，写扩散会引发惊群。由于这是一个新闻平台，名人账号有限，问题没那么严重。对通用型系统而言，则要用混合模型（高关注量账号走读扩散）。

**信息流的滞后：** 由于扩散是通过 Kafka 异步完成的，从帖子发布到出现在关注者信息流里会有一小段延迟。对新闻产品来说这可以接受。

**存储：** 在 Redis 里按用户存 postId 列表而不是完整帖子内容，让内存占用保持在可控范围。完整内容只在填充信息流时才去取。
