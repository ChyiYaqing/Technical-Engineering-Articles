# 设计 YouTube

> 类 YouTube 系统的高层设计全流程讲解。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2062909779576791167](https://x.com/Harry_The_Nerd/status/2062909779576791167) · 2026-06-05

![封面图](https://pbs.twimg.com/media/HKDp-kRaoAAbIxY.jpg)

## 问题范围

我们只关注两条核心链路：**视频上传与视频播放**。认证以及评论、点赞、订阅这类社交功能不在讨论范围内。

**约束与假设：**

- 单个视频最大 1 GB
- 500 万日活用户
- 每个用户每天看 5 个视频 == 每天 2500 万次视频播放
- 10% 的用户每天上传 1 个视频 == 每天 50 万次视频上传
- 原始视频平均大小 300 MB

## 2\. 粗略估算

**原始上传存储量：** 50 万个视频/天 × 300 MB = 每天写入 150 TB 原始视频

**转码后的实际存储量：** 每个视频都要转码成多种分辨率：360p、480p、720p、1080p，可能还有 4K。这会让存储量翻大约 3-4 倍。

实际存储需求：约 450–600 TB/天

**播放：** 每天 2500 万次播放，峰值大约是每秒 290 路视频流。视频字节由 CDN 边缘节点提供，而不是源站，所以源站带宽只占总分发带宽的一小部分。

## 3\. 高层架构总览

系统包含两条并行运行的主要流水线：

**视频流水线：** 负责上传、转码和分发

**元数据流水线：** 负责视频相关的所有结构化数据

这两条流水线松耦合，通过 Kafka 异步通信。

## 4\. 视频上传流程

**第 1 步：生成预签名 URL**

用户选好视频点击上传时，客户端并不会把视频字节发给 API 服务器。客户端是向 API 服务器申请一个预签名的 S3 URL，API 服务器生成后返回给它，客户端再用这个 URL 把原始视频文件直传到 S3。

这一点很关键。让 1 GB 的文件穿过整个 API 服务器集群是一种浪费，会引入不必要的延迟，还会制造瓶颈。直传 S3 能让 API 服务器专注于它擅长的事情，也就是处理轻量请求。

**第 2 步：触发转码流水线**

原始视频落到 S3 后，S3 会发出一个对象创建事件。该事件被发布到一个 Kafka topic 上。转码 worker 从这个 topic 消费消息，开始处理视频。这样整条流水线就是完全异步、彼此解耦的：worker 按自己的节奏处理，系统能平稳应对流量高峰，不会把转码集群压垮。

**第 3 步：转码流水线（DAG 模型）**

视频处理被建模为一个有向无环图（DAG）。

DAG 把处理过程拆成三条支流：

- 视频任务：转码成多种分辨率、打水印、生成缩略图、内容检查
- 音频任务：抽取与编码
- 元数据任务：解析并存储视频元数据

视频文件首先被切成图像组（GoP），也就是一段段可独立解码的短片段。这样做带来两个好处：可以在多个 worker 之间并行处理，以及失败后可以断点续跑。

**流水线包含六个组件：**

**预处理器：** 把视频切成 GoP 分片，为该视频生成 DAG，并把分片放进临时的高速存储（内存或快速缓存层）供后续处理使用。

**DAG 调度器：** 接收生成好的 DAG，将其拆解成一个个离散任务并安排执行。

**资源管理器：** 维护任务队列、worker 队列和运行中队列。它是处理集群的大脑，负责把任务分配给空闲的 worker。

**任务 Worker：** 执行分配到的任务。

**临时存储：** 用于在流水线各阶段之间传递分片的高速中间存储。处理完成后即丢弃。

**编码输出：** 所有目标分辨率的最终转码文件，推送到源站存储，供 CDN 分发。

**第 4 步：完成与元数据更新**

转码完成时，worker 不会直接写元数据数据库，而是往 Kafka 的完成 topic 发布一个完成事件。一个完成处理服务消费该事件，更新元数据数据库和缓存，把视频标记为可播放。

这种解耦是有意为之。worker 直接写库会造成紧耦合，让重试变得更麻烦，还可能在上传高峰期对数据库造成惊群效应。

## 5\. 视频播放流程

播放协议：HLS

YouTube 使用自适应流媒体协议，其中占主导地位的是 HLS（HTTP Live Streaming）。它的工作方式如下：

- 转码后的视频以小片段形式存储，每段通常 2–10 秒
- 生成一个清单文件（M3U8），作为所有可用分辨率下全部分片的索引
- 客户端先下载清单，然后随着播放推进依次拉取分片
- 客户端从不下载完整文件，只比播放头多缓冲几个分片

**自适应码率播放**

播放器持续监测两个信号：可用网络带宽和缓冲健康度（已预加载多少秒视频）。基于这两个信号，播放器自主决定下一个分片要请求哪个分辨率。

M3U8 清单通过包含多个播放列表（每个分辨率一个）来支持这一点。条件变化时，播放器只需切换到另一个播放列表去拉分片即可。这不需要任何服务端事件，完全是客户端逻辑。

**播放链路逐跳拆解**

用户点击播放 -\> 调用 API 服务器

API 服务器从缓存（Redis）或数据库取出视频元数据 -\> 返回 CDN URL 和清单 URL

客户端从 CDN 边缘节点获取 M3U8 清单

客户端开始从 CDN 边缘节点拉取视频分片

如果 CDN 未命中，边缘节点会从源站存储取回该分片并缓存，供后续请求使用

播放器根据带宽和缓冲健康度持续调整分辨率

**CDN（内容分发网络）的重要性**

视频文件是静态内容，对每个观众提供的都是同样的字节。这让它们成为 CDN 的完美候选。一个热门视频只上传一次，就能被缓存到全球数百个边缘节点，被播放数百万次而完全不碰源站。没有 CDN 的话，一个爆款视频会在源站上引发惊群，这个问题光靠水平扩展很难以低成本解决。

## 6\. 数据层

元数据数据库：DynamoDB

视频元数据（标题、描述、上传者 ID、CDN URL、处理状态、时间戳）存在 DynamoDB 中。主要访问模式是按视频 ID 做简单的键值查询，正好契合 DynamoDB 的模型。如果部署的地理分布更广，Cassandra 是个值得考虑的替代方案。

缓存：Redis 搭配 LFU 淘汰

热门视频的元数据缓存在 Redis 中。YouTube 的访问模式高度倾斜：极小一部分视频占据了绝大多数播放量。只要按热度缓存前 20% 的视频，就能拿到很高的缓存命中率，不需要把整个视频库都缓存下来。

这里合适的淘汰策略是 LFU（最不经常使用）。一个连续三天收获数百万播放的爆款视频，应当比一个小时前只被访问过一次的视频更值得留在缓存里。LRU（最近最少使用）会错误地把热门视频淘汰掉，换成那个刚被访问的视频。LFU 才真正契合 YouTube 流量基于访问频次的特点。

## 8\. 关键设计决策汇总

**原始文件上传** -\> 预签名 S3 URL（避免让 GB 级文件穿过 API 服务器）

**流水线触发** -\> S3 事件投递到 Kafka（异步、解耦、可扩展）

**转码模型** -\> DAG 加 GoP 切分（并行与容错）

**播放协议** -\> HLS 加自适应码率（分片分发、客户端侧画质自适应）

**内容分发** -\> CDN（静态内容，极高的缓存命中率）

**元数据存储** \-\> DynamoDB（按视频 ID 的键值访问模式）

**缓存淘汰** -\> LFU（访问模式倾斜）

**服务间通信** -\>Kafka（解耦、异步、可回放）
