# 设计一个分布式键值存储

> 设计一个带分区和复制的分布式键值存储。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2047329176982827353](https://x.com/Harry_The_Nerd/status/2047329176982827353) · 2026-04-23

![封面图](https://pbs.twimg.com/media/HGmIdFPbsAAt_h6.jpg)

分布式键值存储就是一个铺开在数百台机器上的巨型 HashMap——在极大规模下完成存储、读取，并在故障中活下来。Redis、Cassandra 和 DynamoDB 都建立在这些原理之上。下面是完整拆解。

**功能需求**

put(key, value) -\> 存入一个键值对 get(key) -\> 按键取出值 delete(key) -\> 删除一个键值对 复制 -\> 数据能在服务器故障中幸存 分布 -\> 数据分散在多台机器上

**分布数据——一致性哈希**

面对 1000 台机器和数十亿个键，你需要立刻知道某个键落在哪台机器上。一致性哈希把服务器放在一个虚拟环上，每个键顺时针路由到最近的那台服务器：

put("user:123", "Rahul") 哈希 -\> 位置 145 -\> 顺时针 -\> 位于 180 的服务器 B 存储在服务器 B 上 get("user:123") 哈希 -\> 位置 145 → 顺时针 → 位于 180 的服务器 B 以 O(1) 时间从服务器 B 取出

某台服务器挂掉时，只有 1/N 的键需要重新映射，而不是全部。这正是 Cassandra 和 Redis Cluster 内部都采用一致性哈希的原因。

**在故障中幸存——复制**

只存在一台服务器上的数据就是有风险的数据。解决办法是在写入时同时写 N 台服务器，而不是等故障发生后再被动搬数据。生产系统通常用 3 的复制因子——一个主副本、两个副本。主副本挂了，副本上已经有数据了。

put("user:123", "Rahul") 一致性哈希 -\> 服务器 B（主副本）同时写入 -\> 服务器 C（副本 1）同时写入 -\> 服务器 D（副本 2）服务器 B 崩溃 -\> C 和 D 上有数据

一致性 vs 可用性 —— CAP 与法定人数

CAP 定理指出，一个分布式系统只能同时保证三者中的两个：一致性、可用性和分区容错性。网络分区总会发生，所以分区容错性没得商量。真正的选择永远在 C 和 A 之间，而这取决于数据本身。

这由法定人数（quorum）配置来控制：

N = 复制因子 = 3 W = 确认一次写入所需的节点数 R = 确认一次读取所需的节点数 W + R \> N -\> 保证强一致性 银行交易 -\> W=3、R=2 -\> 一致性优先（CP）Twitter 点赞 → W=1、R=1 → 可用性优先（AP）

金融数据需要一致性。社交数据可以容忍轻微的陈旧，换取可用性。面试要的答案是：知道该选哪个，以及为什么。

解决冲突——向量时钟

当两个客户端在不同节点上同时写同一个键时，哪次写入胜出？墙上时钟的时间戳因为时钟偏移而失效——每台机器的时钟都会有微小漂移。向量时钟改用逻辑计数器：

服务器 A 写入 -\> 版本 {A:1} 服务器 B 写入 -\> 版本 {B:1} 服务器 A 写入 -\> 版本 {A:2} {A:2} 胜过 {A:1} -\> 胜负分明 {A:1} 与 {B:1} 是并发的 -\> 冲突，需要解决

冲突解决策略：最后写入者胜出（简单，但可能丢数据）、合并（适用于计数器和购物车），或者推给客户端（让应用来决定，Amazon 的购物车就是这么做的）。

**故障检测——gossip 协议**

面对上千个节点，你不能靠一台中心服务器去挨个探活，那既是瓶颈又是单点故障。取而代之的做法是：每个节点周期性地与几个随机邻居交换健康信息。坏消息会在几秒内自然而然地传遍整个集群，就像流言在办公室里扩散一样。

服务器 A 告诉 B -\> 「服务器 F 已经 10 秒没响应了」服务器 B 告诉 C -\> 「A 和我都联系不上 F」服务器 C 告诉 D -\> 同样的说法 -\> 整个集群在几秒内都知道 F 挂了 分两个阶段：F 静默 10 秒 -\> 疑似宕机 F 静默 30 秒 -\> 确认死亡，键被重新路由

Cassandra 用的正是这一套，每个节点每秒和 3 个随机节点 gossip 一次，不需要中心主节点。

**数据层**

**LSM 树——每个节点上的本地存储**

分布式键值存储本身就是一个数据库，它不会再用另一个数据库来存数据。每个节点用 LSM 树（Log Structured Merge Tree，日志结构合并树）在本地存放自己的键值对，这种结构为快速写入而优化：

write("user:123", "Rahul") -\> MemTable（内存中，快得飞起）-\> 写满后刷入 SSTable（磁盘上）-\> 周期性的 compaction 合并 SSTable，长期保持读取速度

**预写日志（WAL）**

MemTable 活在内存里，一次崩溃就没了。WAL 通过先把每次写入追加到磁盘、再动内存来防止数据丢失。重启时，节点回放 WAL 重建 MemTable。即使硬崩溃也零数据丢失。

write("user:123", "Rahul") 1. 追加到磁盘上的 WAL（快速的顺序写）2. 写入内存中的 MemTable 3. 服务器崩溃 -\> MemTable 没了 4. 重启 -\> 回放 WAL -\> MemTable 重建完成

**Zookeeper —— 配置与协调**

存放哈希环的映射关系、复制因子、法定人数配置（W 和 R）以及集群成员信息。所有节点都监听 Zookeeper 以获取实时变更。gossip 协议把节点健康状态回传给 Zookeeper，使环映射保持最新。

**可扩展性**

往环上加节点。一致性哈希会自动只重新分布受影响的那些键，不需要重排整个数据集。水平扩展的协调开销几乎为零。

延迟

写入先落到 MemTable（内存中），写延迟是微秒级的。读取并行查询 R 个节点，返回最快的那个有效响应。WAL 的写入是磁盘顺序写——磁盘上最快的操作方式。

可用性 复制因子为 3 意味着系统能容忍最多 2 个节点同时故障而不丢数据。gossip 协议在几秒内发现故障，Zookeeper 随即更新环映射，协调者就会自动停止把请求路由到死掉的节点上。
