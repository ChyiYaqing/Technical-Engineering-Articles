# 设计一个限流器

> 大规模限流的算法与架构。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2045533839649624096](https://x.com/Harry_The_Nerd/status/2045533839649624096) · 2026-04-18

![封面图](https://pbs.twimg.com/media/HGMuQa-aYAE1tV5.jpg)

限流器保护你的系统不被垃圾请求、行为异常的客户端，或者仅仅是一次突发流量给压垮。我们来设计一个快速、公平、可上生产的限流器。

**功能需求**

系统必须具备三种行为：

1\. 统计每个用户在一个时间窗口内的请求数 2. 未超过限额就放行 3. 超过限额则返回 HTTP 429 Too Many Requests，并带上 Retry-After 响应头

Retry-After 头会明确告诉客户端，还要等多少秒才能再试。

它究竟放在哪儿？

放在 API 网关内部，或者紧挨在网关之前，但绝不能放在网关之后。限流的全部意义就是在请求打到你的服务之前把它拦下来。一旦请求越过了网关，伤害已经造成了。

在大多数系统里，限流器就作为中间件住在 API 网关内部。所以网关干两件事：限流和路由。

**计数难题，也就是为什么单台服务器不够用**

第一反应可能是在每台服务器上放一个 HashMap，用 userID 映射到一个计数器。但规模上去之后你会有多台服务器，每台都有自己的 HashMap：

用户 X -\> 服务器 1 -\> 计数 = 1 用户 X -\> 服务器 2 -\> 计数 = 1 用户 X -\> 服务器 3 -\> 计数 = 1

用户实际发了 3 次请求，但每台服务器都以为只发了 1 次。限流被绕过了。

计数器必须放在一个所有服务器都能访问的中心化位置。

Redis 是这里的正确工具 Redis 就是答案。它是中心化的、内存型的，而且开箱即用地提供了你需要的一切：

INCR 命令——原子地递增计数器，不会有竞态条件 TTL——让计数器在 60 秒后自动过期，不需要清理任务 微秒级读取——给每个请求增加的开销不到 1 毫秒

请求到达

↓

查 Redis —— "userX:counter" 存在吗？

↓

不存在 → 创建，计数 = 1，TTL = 60 秒 → 放行

存在 → INCR 计数器

↓

计数 ≤ 限额 → 放行

计数 \> 限额 → 拒绝，返回 429

**数据库层——两个存储**

**Redis（主存储）**

存放计数器和请求时间戳。它天然是易失（临时）的，Redis 重启后计数器会清零，这可以接受。规则会在启动时从配置库重新加载到缓存里。

**配置库（持久化存储）** 总得有人来定义规则，比如免费档每小时 100 次请求、付费档 10,000 次、验证码接口每 10 分钟 3 次。这些规则存在 PostgreSQL 这样的持久化数据库里：

表结构：userID tier endpoint maxRequests windowSeconds

限流器在启动时读取这些规则并缓存进 Redis，这样每一次判定都完全在 Redis 里完成，耗时微秒级，运行期完全不用碰配置库。

四种窗口算法

你如何定义和执行时间窗口，影响非常大。有四种经典做法，各有各的权衡。

1\. 固定窗口

把时间切成固定的 60 秒桶。到边界时计数器清零。实现简单，但有个众所周知的缺陷（就在窗口边界处）：

窗口 1：请求发生在第 55、56、57、58、59 秒 -\> 5 次

窗口 2：请求发生在第 1、2、3、4、5 秒 -\> 5 次

10 秒内发了 10 次请求，是限额的两倍。可两个窗口都认为一切正常。

2\. 滑动窗口

始终看「从当前时刻往前的 60 秒」，是一个随时间滚动的窗口。没有边界 bug，公平得多。在 Redis 里，把每次请求的时间戳存进有序集合，然后统计落在最近 60 秒内的数量。大多数生产系统用的是这种。

3\. 令牌桶

想象一个装令牌的桶。令牌以固定速率加入，比如每秒 10 个，最多攒到 100 个。每个请求消耗一个令牌。桶空了，请求就被拒绝。

桶容量：100 个令牌

补充速率：10 个令牌/秒

请求到达 -\> 有令牌吗？-\> 消耗 1 个，放行 -\> 桶空了？-\> 拒绝，返回 429

关键优势是：它天然允许短时突发。如果一个用户有一阵子没发请求，他的桶是满的，就可以瞬间打出 100 个请求。这非常适合那些突发行为本身合理的 API，比如开发者跑一个批处理任务。

使用者：Stripe、AWS API Gateway。

4\. 漏桶

请求进入一个队列（也就是桶）。不管它们到得多快，都以固定速率处理，比如每秒 10 个。队列满了，新请求就被丢弃。

请求以任意速率涌入 -\> 队列 → 以固定的 10 req/s 处理

\-\> 队列满了？-\> 丢弃请求

输出永远是平滑且可预测的，任何突发都穿不过去。这非常适合下游服务需要稳定、受控流量的场景，比如扛不住尖峰的支付处理系统。

代价是：突发但合理的流量会被排队甚至丢弃，用户可能觉得不公平。

该用哪一种？

1\. 固定窗口——简单，只用在非关键的内部工具上

2\. 滑动窗口——最公平，最适合面向用户的 API

3\. 令牌桶——当突发可以接受时最合适（开发者 API）

4\. 漏桶——当下游需要稳定流量时最合适（支付、计费）

**非功能需求**

**可扩展性**

限流器服务器可以水平扩展。Redis 通过 Redis Cluster 扩展，把键空间切分到多个节点上。用户 A 的计数器在节点 1，用户 B 的在节点 2。负载被干净地分摊，没有单点瓶颈。

**延迟**

限流器位于每一个请求的关键路径上，所以它一慢，你整个系统都会感觉慢。Redis 能把这次检查控制在 1 毫秒以内。规则在启动时就缓存进 Redis，运行期零数据库访问。这点开销对用户来说基本是不可见的。

**可用性**

Redis 挂了会怎样？两个选择：

失败放行（fail open）——放行所有请求。系统还活着，但保护暂时失效。

失败拒绝（fail closed）——拒绝所有请求。系统受到保护，但谁也用不了。

大多数生产系统选择失败放行。几秒钟不受保护的流量，远好过整个系统对所有用户彻底黑屏。
