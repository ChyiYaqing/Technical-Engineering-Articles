# 设计一个聊天系统

> 一个实时聊天应用的系统设计。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2061445321910284589](https://x.com/Harry_The_Nerd/status/2061445321910284589) · 2026-06-01

![封面图](https://pbs.twimg.com/media/HJtz5p3bsAAvAYI.jpg)

## 问题描述

设计一个像 WhatsApp、微信或 Messenger 那样的实时聊天系统。用户应能即时收发消息，支持单聊和群聊，并带有送达回执和在线状态提示。

## 需求与范围

**功能需求：**

- 单聊和群聊（每群最多 1024 人）
- 消息实时送达
- 送达回执：已发送（单勾）、已送达（双勾）、已读（蓝勾）
- 在线状态与最后上线时间
- 媒体支持（图片、视频，高层次上）
- 消息搜索

**非功能需求：**

- 1000 万 DAU
- 高可用、低延迟
- 送达回执可接受最终一致性
- 消息绝不能丢失

**不在范围内：** 端到端加密、通话、动态。

## 容量估算

DAU - 1000 万 每用户每日消息数 - 50 每日消息总量 - 5 亿 每秒消息数 ~5000 条/秒 平均消息大小（文本）~100 字节 写吞吐 ~500 KB/秒 有效操作数/秒 ~10000（存储 + 投递） 并发 WebSocket 连接数 ~200 万（20% DAU 活跃） 所需聊天服务器实例数 ~40（每台承载 5 万连接）

**协议选择：WebSocket**

HTTP 是请求-响应式的：客户端问，服务端答。而聊天要求消息一到达服务端就被推送给客户端。可选项有：

- **短轮询：** 客户端每 N 秒问一次。1000 万用户每 5 秒轮询一次，光轮询就是 200 万请求/秒，不可接受。
- **长轮询：** 客户端挂住连接直到有消息到来。好一些，但仍是半双工，规模上来代价很高。
- **WebSocket：** 全双工、长连接、双向。服务端可即时推送。WhatsApp、Messenger 和 Slack 用的都是它。

每台聊天服务器维持约 5 万个并发 WebSocket 连接。按约 200 万并发用户算，负载均衡器后面大约需要 40 台聊天服务器实例。

## **核心设计：存储转发**

消息在尝试投递之前一定先持久化到 Cassandra，这一点没得商量。如果接收方设备在投递途中挂了，消息必须还在。流程永远是：先写入，再投递，绝不为了乐观提速而跳过持久化。

写路径（发送方在线）

发送方通过自己的 WebSocket 连接把消息发给 **聊天服务器 A**

聊天服务器 A 为该消息生成一个唯一的 **Snowflake ID**（可按时间排序、分布式生成）

聊天服务器 A 把消息发布到 **Kafka**

聊天服务器 A 立即向发送方返回单勾确认，意思是「我们收到了」

**投递 worker** 消费 Kafka，并把消息可靠地写入 **Cassandra**

在 **在线状态存储（Redis）** 中查询接收方的在线状态

**如果接收方在线：**

- worker 通过 Redis Pub/Sub 找出接收方连在哪台聊天服务器上
- 向该频道发布投递事件
- **聊天服务器 B** 通过 WebSocket 把消息推给接收方
- 接收方设备通过 WebSocket 回送 ACK
- 聊天服务器 A 通知发送方，双勾出现

**如果接收方离线：**

- 消息已经安全地存在 Cassandra 里
- worker 触发 **通知服务** 向接收方设备发送推送通知
- 接收方重新上线时，客户端从 Cassandra 拉取错过的消息
- ACK 经 WebSocket 回流，双勾更新

**已读回执（蓝勾）：**

- 由接收方打开该会话时触发
- 客户端通过 WebSocket 发送已读事件
- 聊天服务器更新 Cassandra 中的消息状态
- 发送方收到通知，蓝勾出现

## 跨服务器消息路由

在 40 台聊天服务器实例的规模下，发送方和接收方很少连在同一台服务器上。聊天服务器用 **Redis Pub/Sub** 解决这个问题：每台服务器订阅它所连接用户对应的频道。当投递 worker 需要把消息推给连在服务器 B 上的接收方时，它向该用户的 Redis 频道发布消息，服务器 B 取到后通过 WebSocket 投递出去。

## 在线状态

每个客户端每 5 秒向它所连的聊天服务器发一次心跳 ping。服务器更新 Redis 键 presence:{userId}，写入当前时间戳并设置 15 秒的 TTL。如果连续漏掉 3 次心跳，TTL 到期，用户被自动标记为离线——不需要显式登出。「最后上线时间」就是最后一次记录到的心跳时间戳。

## 数据库选型

**Cassandra（消息存储）** - 按 conversationId 分区，按时间戳排序，范围读是 O(1)。写吞吐一流。Facebook Messenger 就用它。

**Redis（KV）（在线状态存储）** - 亚毫秒级读取，基于 TTL 的过期实现自动离线检测

**Redis Pub/Sub（跨服务器路由）** - 轻量、快，而且技术栈里本来就有

**Elasticsearch（消息搜索）** - 消息全文检索，由 CDC 管道从 Cassandra 异步同步

**为什么消息偏偏选 Cassandra：** 核心访问模式是「取出会话 X 中的所有消息，按时间戳排序，从偏移量 Y 开始」。Cassandra 按 conversationId 分区，一个会话的所有消息落在同一个节点上；分区内部行按时间戳排序，因此范围读极快。它也能从容扛住约 5000 次/秒的写入。

## **群聊**

对于最多 1024 人的群，扩散发生在投递 worker 这一层。当一条群会话消息进入某个 Kafka 分区时：

worker 从 **群组服务**（由 SQL 数据库支撑）取出完整成员列表

对每个成员，worker 在 Redis 中检查其在线状态

在线成员通过 Redis Pub/Sub 走 WebSocket 投递

离线成员收到推送通知

消息只在群 conversationId 下往 Cassandra 写一次，不按成员重复存储

这套做法在 1024 人上限内运转良好。超过之后，扩散会变成惊群问题，就需要混合方案（超大群走读扩散）。

## 媒体处理

文本消息走 WebSocket -\> Kafka -\> Cassandra 这条流水线。媒体（图片、视频）单独处理，以保持消息管道的轻量：

- 客户端通过预签名 URL 把媒体文件直传 **S3**
- S3 存储原始资源，并触发向 **CloudFront（CDN）** 的分发
- 聊天消息里只包含媒体 URL 和元数据，不含二进制内容
- 接收方直接从 CloudFront 取媒体，不经过聊天服务器

这样 WebSocket 服务器就不必承载大负载数据，而 CDN 边缘节点可以在全球范围内规模化地分发媒体。

## 消息搜索

一条 CDC（变更数据捕获）管道跟踪 Cassandra 的写入，把新消息异步同步到 **Elasticsearch**。用户搜索消息时打到的是由 Elasticsearch 支撑的独立搜索服务，与实时投递路径完全解耦。这样就不会把全文检索的负载压给 Cassandra——它本来也不是为此设计的。

## 认证与限流

认证在 **负载均衡器 / API 网关** 这一层用 JWT token 完成。WebSocket 升级握手时在查询串或请求头里带上 token，网关在连接建立前先校验。发消息的限流按用户维度强制执行，以防滥用并保护 Kafka 不被写入尖峰冲击。

## 瓶颈与权衡

**投递延迟 vs 持久性：** 先落盘 Cassandra 再投递会增加一点延迟。这是正确的权衡：稍慢一点的投递永远好过丢一条消息。

**跨服务器路由的复杂度：** Redis Pub/Sub 给跨服务器投递多加了一跳。在 40 台服务器的规模下这可以接受，但随着集群变大，更成熟的服务网格或一致性哈希方案（把用户确定性地路由到某台服务器）就值得上了。

**群扩散的天花板：** 1024 人上限是一个架构约束。超过之后，按成员逐个扩散的投递 worker 代价会很高。超大群的广播更适合用发布/订阅树形模型，而不是扁平扇出。

**在线状态的准确性：** 基于心跳的在线状态有约 15 秒的误差窗口。一个刚掉线的用户最多会有 15 秒仍显示在线。这是所有主流聊天系统都已知并接受的权衡。
