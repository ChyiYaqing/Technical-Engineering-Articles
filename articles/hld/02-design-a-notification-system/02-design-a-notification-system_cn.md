# 设计一个通知系统

> 一个可扩展的多渠道通知系统的系统设计。
>
> 原文：[https://x.com/Harry_The_Nerd/status/2044839667267494292](https://x.com/Harry_The_Nerd/status/2044839667267494292) · 2026-04-16

![封面图](https://pbs.twimg.com/media/HGC6vPzawAAn4-y.jpg)

通知系统支撑着你用的每一个应用：WhatsApp 的提示音、Instagram 的点赞、验证码（OTP）、IPL 比分提醒。我们来拆解一个能扩展到百万级用户的设计。

**功能需求**

三件事：

1\. 用户可以订阅这个系统 2. 系统捕获事件（一次点赞、一次比赛比分更新、一次验证码触发）3. 系统把通知投递给订阅者

**通知渠道** 一条通知可以通过四种渠道触达用户：1. 推送通知——手机屏幕上弹出的那种 2. 邮件——落到收件箱里 3. 短信——文本消息，用于验证码和告警 4. 应用内通知——那个带红点的小铃铛

每个渠道都有自己独立的服务，它们不该塞进同一个单体应用。它们的扩展方式不同、故障相互独立、延迟要求也不一样。

**这是路由器，不只是 API 网关**

在 Kafka 和各渠道服务之间，坐着一个通知路由器（Notification Router）。它看起来像 API 网关，但里面固化了真正的业务逻辑：

「这个用户关掉了短信 -\> 跳过短信」

「这是一条验证码 -\> 不管用户偏好如何，一律走短信」

「推送失败 -\> 回退到邮件」

API 网关只会按 URL 盲目转发，而路由器认识每一个用户。

**数据库层——你需要两个**

**用户偏好库**

在发送任何东西之前，路由器需要知道：这个用户想要哪些渠道？他订阅了哪些通知？他的设备推送 token 是什么？这个库回答上述所有问题。把它缓存在 Redis 里，这样路由器就不必为每一条通知都去查数据库。

**通知日志库**

每一条发出去的通知都会记在这里——notificationID、userID、渠道、内容、状态（已发送 / 已送达 / 失败）以及 created\_at。追踪服务在每次发送后写入这张表。

规模问题，以及为什么 Kafka 能解决它

想象一下 IPL 赛季，Bumrah 拿下一个三柱门。1000 万用户需要在同一秒收到通知。如果事件直接打到各渠道服务上，它们会被压垮。

解决办法是消息队列——Kafka。事件先进队列，渠道服务按自己的节奏消费。队列在流量尖峰和你的服务之间充当缓冲。

可以把它想象成一家餐厅。没有排队机制时，100 个客人同时进门会让厨房崩溃；有了取号系统，厨房就能全速而平稳地处理订单。

用 Kafka 还意味着：某个渠道服务挂掉时，消息不会丢。它们会留在 Kafka 里，直到服务恢复。

完整架构

订阅者 → 用户偏好库

↓

事件捕获服务

↓

Kafka（消息队列）

↓

通知路由器 → 查询用户偏好库

↓

推送 / 邮件 / 短信 / 应用内 服务（并行）

↓

追踪服务 → 通知日志库

投递之后——追踪

通知发出去之后，你想知道三件事：

1\. 送达了吗？有没有到达设备？2. 被打开了吗？用户点开了没有？3. 失败了吗？token 错误、邮件退信、短信丢失？

失败的通知会触发带指数退避的重试逻辑——1 秒后重试，然后 2 秒，然后 4 秒。如果所有重试都失败，就回退到另一个渠道。这叫优雅降级。

投递数据也能反哺产品团队——打开率、最佳发送时间、通知疲劳的信号。而且短信和邮件每发一条都要花钱，所以每一条都得记账。

**非功能需求**

**可扩展性**

每个渠道服务都可以独立地水平扩展。短信的流量尖峰不会影响推送服务。Kafka 天然会把负载分摊到每个消费者组里的多个消费者上。

**延迟**

Kafka 是异步的，会带来一点延迟，这对大多数通知来说没问题。真正的延迟收益来自把用户偏好缓存在 Redis 里，让路由器永远不必冷启动去查数据库。

补充：验证码是例外。它需要近乎即时的送达，所以完全绕过 Kafka，直接进短信服务。

**可用性**

三层保护：

1\. Kafka 复制——消息会在多个 broker 之间复制。挂掉一个 broker，消息不丢。

2\. 带指数退避的重试，发送失败会自动重试。

3\. 回退渠道，推送失败？试邮件。邮件失败？试短信。系统会优雅降级，而不是干脆把通知丢掉。
