## 高层设计：Instagram

## 1\. 需求

功能性需求

- 上传照片和视频
- 关注与取消关注用户
- 点赞、评论和分享帖子
- 信息流生成：为每个用户生成个性化、带排序的信息流
- 搜索帖子、话题标签和用户
- 通知：点赞、评论、关注、提及

不在讨论范围

- 直播
- 私信
- Reels（另有一套重推荐的视频流水线）
- Stories（架构上与帖子类似，只是多了存活时间，可作为扩展加上）

非功能性需求

- 高可用：信息流和媒体分发绝不能宕机
- 低延迟：信息流加载要在 100ms 以内，媒体在 200ms 以内
- 巨大的读吞吐量：读写比约为 1000:1
- 信息流、点赞数和通知可以接受最终一致性
- 关注/取关和用户资料数据需要强一致性

## 2\. 容量估算

- **日活用户：** 5 亿
- **每日发帖量：** 20% 的日活用户每天发帖，即 1 亿条帖子/天
- **帖子平均大小：** 约 5 MB（照片约 1 MB、视频约 10 MB 的加权平均）
- **每天的原始存储量：** 1 亿 × 5 MB = **500 TB/天**
- **每年的原始存储量：** 约 180 PB（尚未计入副本和多分辨率变体）
- **读写比：** 约 1000:1 —— 一条名人帖子会被观看数亿次

读写的不对称是这个设计中最重要的一个数字。一次发帖，可能带来十亿次读取。它驱动着每一个架构决策：激进的缓存、边缘的 CDN、预计算的信息流，以及到处都是的只读副本。整个系统压倒性地为读做优化。

热门媒体的 CDN 命中率约为 90%，意味着绝大多数媒体读请求根本不会到达源站基础设施。

## 3\. API 网关

所有客户端请求——iOS、Android、网页或第三方集成——都经由 API 网关进入。它的职责是：

- **认证与授权：** 在请求到达任何下游服务之前校验 token
- **限流：** 保护下游服务不受流量高峰和滥用的冲击
- **请求路由：** 把请求分发到正确的微服务
- **SSL 终结：** 在边缘处理 HTTPS

关键约束和 Spotify 一样：API 网关绝不能出现在二进制媒体负载数据的链路上。一次视频上传可能有 100MB 甚至更多，让它穿过 API 网关会造成灾难性的瓶颈。网关只负责认证和路由，媒体上传则通过下面要讲的直传 S3 预签名 URL 模式来完成。

## 4\. 上传流水线

上传流水线是系统中最复杂的写路径。它和 Spotify 的转码流水线（第 15 篇）非常相似，但在图片分辨率和视频格式上有 Instagram 特有的要求。

**第 1 步：认证与生成预签名 URL**

客户端向 API 网关发送上传请求，网关对用户做认证，然后转发给 **Post 服务**。Post 服务生成一个**预签名 S3 URL**，这是一个有时效、已认证的 URL，允许客户端直接把文件传到 S3，二进制负载数据不经过任何后端服务。预签名 URL 被返回给客户端。

这个模式是根本性的。我们的后端从不接触原始媒体文件，它只处理元数据和编排。这让 Post 服务保持轻量、无状态、可水平扩展。

**第 2 步：客户端直传 S3**

客户端用预签名 URL 把原始媒体文件直接传到 S3，这是一条客户端到 S3 的直连。上传完成后，S3 发出一条事件。

**第 3 步：转码**

S3 的上传事件经由 Kafka 触发**转码服务**。转码服务按媒体类型分别处理：

**对于图片：**

- 生成多个分辨率变体：用于个人主页九宫格的缩略图（150×150）、用于信息流展示的中等尺寸（640×640），以及用于展开查看的原图
- 施加压缩和格式优化（面向 Web 客户端用 WebP，面向老客户端用 JPEG）
- 生成一张模糊占位图（在完整图片渲染出来之前立刻加载的低画质预览）

**对于视频：**

- 生成多个画质变体：360p、480p、720p、1080p
- 把视频切成 HLS 分片（与 Spotify 类似），支持自适应码率播放
- 生成一帧缩略图用于信息流预览
- 施加压缩

所有变体都写回 S3。目录结构是确定的 —— media/{post\_id}/{variant}/，因此任何服务都能直接拼出正确的 URL，无需查询。

**第 4 步：Kafka 扇出**

转码完成后，转码服务向 Kafka 发布一条 post.transcoded 事件。两个消费者各自独立地接收它：

**元数据 Worker：** 把帖子元数据写入 Posts 数据库，并填充 Redis 中的帖子元数据缓存。

**搜索索引 Worker：** 把新帖子索引进 Elasticsearch，让它在几秒内就能通过搜索和话题标签被找到。

这种事件驱动的扇出让所有下游服务保持解耦。如果搜索索引 Worker 临时挂掉，它只是在自己的 Kafka offset 上落后，恢复后追上来即可，不丢数据，也不影响任何其他服务。

**第 5 步：信息流扇出**

第三个 Kafka 消费者（**信息流扇出 Worker**）接收 post.transcoded 事件，开始把新帖子写入作者所有粉丝的信息流。这就是下面「信息流生成」一节要详细讲的写扩散过程。

**上传流水线中的瓶颈**

转码服务是主要瓶颈，生成多种图片分辨率和视频画质变体非常吃 CPU。缓解办法是把转码服务做成从 Kafka topic 拉任务的、可水平扩展的 worker 池。每个转码任务彼此独立，因此能线性扩展。S3 的上传吞吐不是瓶颈，S3 本来就是为这种量级设计的。

## 5\. 媒体分发与 CDN

媒体一旦进了 S3 并完成转码，分发就很直接了，但必须极快且全球分布。

一层 **CDN**（CloudFront 或 Akamai）挡在 S3 前面。客户端的每个媒体请求都先打到最近的 CDN 边缘节点。缓存命中时（热门帖子大约 90% 的请求如此），CDN 直接返回媒体，源站完全不参与。未命中时，CDN 从 S3 取回、在边缘缓存下来，再返回。

CDN 命中率之所以这么高，是因为 Instagram 的内容服从幂律分布：极小一部分帖子（名人帖、爆款内容）占据了绝大多数浏览量。这些帖子在上传后几乎立刻就会被缓存到边缘节点，并保持热度好几天。

对于媒体请求，客户端总是根据当前展示场景请求对应的分辨率变体：九宫格视图用缩略图 URL，信息流用中等尺寸 URL，展开查看用原图 URL。它们是不同的 S3 对象，对应不同的 CDN 缓存条目，这意味着 CDN 可以为每个场景提供成本最低且合适的那个变体。

## 6\. 信息流生成

信息流生成是 Instagram 架构中最难的分布式系统问题。挑战在于：一个用户关注了 500 个账号，每个账号每天发两条，光这一个用户每天就有 1000 条潜在相关帖子。再乘以 5 亿用户。系统必须在用户打开 App 的那一刻，在 100ms 内为每个人送上个性化、排好序的信息流。

有两种基本策略，Instagram 用的是二者的混合。

**策略 1：写扩散（推模型）**

用户发帖时，信息流扇出 Worker 立刻把这条帖子写进其每一位粉丝的预计算信息流中。每位粉丝的信息流是一个 **Redis 有序集合**，结构如下：

- **Key：** feed:{user\_id}，例如 feed:500
- **Member：** post\_id
- **Score：** 一个综合相关性得分，结合了时新性（Unix 时间戳）和互动信号（点赞数、评论数、粉丝与作者之间的亲密度）

ZREVRANGE feed:500 0 19 用一次 Redis 调用就能按分数降序返回用户 500 的前 20 条帖子 ID。这极快，在亚毫秒级。

每个用户的信息流有序集合上限约 1000 条帖子，更旧、分数更低的帖子会被自动淘汰。用户很少往下刷过 20-30 条，所以 1000 这个上限已经相当宽裕。

**纯写扩散的问题：** 一位有 1 亿粉丝的名人发了张照片，信息流扇出 Worker 就得写 1 亿个 Redis 有序集合。哪怕每次写只要 1 微秒，一条帖子的扇出也要 100 秒。这完全不可接受。

**策略 2：读扩散（拉模型）**

对于名人和高粉丝量账号（超过某个阈值，比如 100 万粉丝），就放弃写扩散。他们的帖子改为存进一个单独的**名人帖子** Redis 缓存，以用户 ID 为键。当粉丝打开信息流时，系统实时从其关注的所有名人账号拉取最新帖子，再与预计算好的信息流合并。

**混合模型**

Instagram 采用混合方案：

- **普通用户**（粉丝数低于阈值）：写扩散。帖子立刻推入粉丝的信息流有序集合。
- **名人用户**（粉丝数高于阈值）：读扩散。帖子存进名人帖子缓存，在读取时合并进粉丝的信息流。

在信息流读取时，Feed 服务会：

从 Redis 取出预计算的信息流有序集合。ZREVRANGE feed:{user\_id} 0 49

从名人帖子缓存中取出该用户关注的所有名人账号的最新帖子

把两个列表合并并重新排序

把排名前 20 的帖子 ID 返回给客户端

**信息流填充（Hydration）**

信息流读取返回的是帖子 ID，不是可直接渲染的内容。客户端需要真实的帖子数据来展示。Feed 服务用一次 MGET 调用，从 Redis 中的**帖子元数据缓存**取数据来填充这些帖子 ID：

MGET post:101 post:202 post:303 ... post:2020

MGET 用一次往返就取回全部 20 条记录，而不是发 20 次顺序调用。这一点很关键：20 次顺序缓存调用每次 1ms，光这一步就吃掉了 100ms 预算中的 20ms，而客户端还什么都没拿到。

若某条帖子缓存未命中，Feed 服务会回落到 Posts 数据库取出缺失的记录，再写回 Redis。

最终返回给客户端的响应包含帖子元数据、媒体 URL（指向 CDN）、作者信息以及点赞/评论数——渲染信息流所需的一切都齐了。

**信息流生成中的瓶颈**

主要瓶颈是普通用户在爆红时刻的扇出 Worker：某个中等热度的用户（比如 50 万粉丝）突然爆火并频繁发帖，扇出队列增长的速度可能超过 worker 的处理速度。缓解办法是水平扩容扇出 Worker 池，并优先处理在线用户——给一个三天没打开 Instagram 的用户写信息流毫无意义。

次要瓶颈是 Redis 内存。为 5 亿用户各存 1000 条帖子 ID 需要相当可观的内存。这靠激进的 TTL 策略来管理：不活跃用户的信息流会从 Redis 中淘汰，等他们下次登录时再从 Posts 数据库重建。

## 7\. Post 服务与数据模型

Post 服务负责帖子的增删改查，也是上传流程的入口。

Posts 表（PostgreSQL）

Posts post\_id UUID, primary key user\_id UUID, foreign key -\> Users caption TEXT media\_type ENUM('photo', 'video', 'carousel') media\_url TEXT (base S3/CDN path) posted\_at TIMESTAMP like\_count INTEGER comment\_count INTEGER

like\_count 和 comment\_count 是直接存在帖子行上的反范式计数器。每次加载信息流都去查 Likes 表来数点赞数会慢到不可接受。取而代之的是，点赞和评论事件通过 Kafka 消费者异步地递增这些计数器。

Users 表（PostgreSQL）

Users user\_id UUID, primary key username VARCHAR, unique full\_name VARCHAR profile\_pic\_url TEXT bio TEXT follower\_count INTEGER following\_count INTEGER created\_at TIMESTAMP

follower\_count 和 following\_count 同样是反范式计数器，在关注/取关事件发生时异步更新。

Follows 表（PostgreSQL）

Follows follower\_id UUID, foreign key -\> Users followee\_id UUID, foreign key -\> Users created\_at TIMESTAMP PRIMARY KEY (follower\_id, followee\_id)

关注关系是一张多对多的关联表。关注是一次 INSERT，取关是一次 DELETE。「给我用户 X 关注的所有人」就是 WHERE follower\_id = X。简单、快、有索引。

对于二度、三度关系，比如互相关注、推荐用户、好友的好友，**图数据库**（Neo4j 或 AWS Neptune）比关系型关联表更合适，因为在数百万节点上做图遍历在 SQL 里代价极高，在图数据库里却是原生能力。

Likes 与 Comments 表（PostgreSQL）

Likes like\_id UUID post\_id UUID, foreign key -\> Posts user\_id UUID, foreign key -\> Users created\_at TIMESTAMP Comments comment\_id UUID post\_id UUID, foreign key -\> Posts user\_id UUID, foreign key -\> Users content TEXT created\_at TIMESTAMP

这些表存的是原始互动数据。帖子行上的点赞数和评论数则以异步反范式计数器的方式维护：「用户 X 是否给帖子 Y 点过赞」的唯一真实来源是 Likes 表，但展示出来的数字来自那个反范式列。

## 8\. 搜索服务

Instagram 的搜索覆盖三类实体：帖子（按文案和话题标签）、用户（按用户名和全名），以及作为一等对象的话题标签。

**存储引擎：Elasticsearch**

Elasticsearch 能同时在这三类实体上处理全文搜索、模糊匹配、部分匹配和相关性排序。搜索 "har" 可以返回用户名为 "harry\_spidey" 的用户、文案为 "harbour at sunset" 的帖子，以及话题标签 "#harmony"，并统一按相关性排序。

**Elasticsearch 文档**

**帖子文档：**

```
{
  "post_id": "123",
  "caption": "beautiful sunset in Goa",
  "hashtags": ["sunset", "goa", "travel"],
  "user_id": "456",
  "like_count": 50000,
  "comment_count": 3200,
  "posted_at": "2026-06-10T18:00:00Z",
  "author_follower_count": 2000000
}
```

**用户文档：**

```
{
  "user_id": "456",
  "username": "harry_dev",
  "full_name": "Harry Singh",
  "follower_count": 15000,
  "verified": false
}
```

**按互动量加权的排序**

Spotify 的排序纯粹看文本相关性，Instagram 的搜索则不同，它把文本匹配得分与互动信号结合起来。一条与查询匹配度不高但有 5 万点赞的帖子，排名会高过一条完全匹配但只有 3 个赞的帖子。对于用户搜索，粉丝数和认证状态是主要排序信号：搜 "harry" 会优先浮现已认证、高粉丝量的账号。

话题标签是一等的搜索实体。#sunset 是一个索引词条，串起成千上万条帖子。点击文案里的话题标签会触发一次针对 Elasticsearch 中 hashtags 字段的搜索，返回所有打了该标签的帖子，按互动量排序。

**保持 Elasticsearch 同步**

搜索索引 Worker 从 post.transcoded 这个 Kafka topic 消费新帖子，并从另外的 post.updated 和 user.updated topic 消费更新。点赞数的变化会先攒批，再周期性同步到 Elasticsearch，而不是每点一次赞就同步一次——搜索结果里的点赞数并不需要精确实时。

热门搜索查询（搜顶流名人、热门话题标签）会以较短的 TTL 缓存在 Redis 中，避免 Elasticsearch 被一模一样的查询反复轰炸。

**搜索中的瓶颈**

当查询量非常高、又同时在多个字段上开启模糊匹配时，Elasticsearch 的性能会下降。缓解手段是组合拳：用 Redis 缓存热门查询、水平扩展 Elasticsearch 集群，以及索引调优——索引中只保留搜索和排序需要的字段，而不是整个帖子文档。

## 9\. 通知服务

系统中的每一次互动（点赞、评论、关注、提及、分享）都可能触发一条通知。在 Instagram 的量级上，这是一条量极大的事件流。

通知触发场景

- 用户 A 给用户 B 的帖子点赞 -\> 通知用户 B
- 用户 A 评论用户 B 的帖子 -\> 通知用户 B
- 用户 A 关注用户 B -\> 通知用户 B
- 用户 A 在评论中提及用户 B -\> 通知用户 B
- 用户 A 分享用户 B 的帖子 -\> 通知用户 B

**架构：Kafka 扇出**

每个互动服务（点赞服务、评论服务、关注服务）都往各自的 Kafka topic 发布事件。通知服务独立地订阅它们全部。这与系统中其他地方用的是同一套事件驱动扇出模式。点赞服务并不知道、也不关心通知服务的存在。

**通知合并**

对一条有 5 万点赞的帖子，每个赞推一条通知会是灾难。通知服务改为施加**合并**——把多条相似事件合成一条通知：

- 「Harry 和另外 499 人赞了你的帖子」，而不是 500 条单独的通知
- 「你的帖子有 5 条新评论」，而不是 5 次独立推送

合并在一个短时间窗口内生效。同一条帖子上 30 秒窗口内的事件会先攒成一批再投递。

**设备令牌存储**

通知服务维护一个简单的数据存储，映射 user\_id -\> device\_token, platform (ios/android)。每当用户在新设备上登录时，这份数据就会更新。

**最后一公里投递：APNs 与 FCM**

通知服务不能直接推送到手机设备，这条投递通道由 Apple 和 Google 掌控。流程是：

通知服务收到 Kafka 事件

从令牌存储中取出用户的设备令牌

如果适用，先做合并

带着通知负载数据调用 **APNs**（Apple 推送通知服务，面向 iOS 设备）或 **FCM**（Firebase 云消息，面向 Android 设备）

由 APNs/FCM 完成到设备的实际投递

互动事件 -\> Kafka -\> 通知服务 -\> 取设备令牌 -\> 如适用则合并 -\> APNs（iOS）/ FCM（Android） -\> 用户锁屏

对于应用内通知（那个通知铃铛），通知服务还会往 PostgreSQL 的**通知表**里写一条记录，客户端在打开时通过轮询或 WebSocket 连接拿到它。

通知服务中的瓶颈

瓶颈在爆款事件的扇出：一条名人帖子一小时内产生 100 万个赞，就意味着通知服务要处理 100 万条 Kafka 事件。合并能极大压缩真正推出去的通知数量，但事件处理的吞吐量仍然必须够高。实践中靠水平扩容通知服务 worker 和更激进的合并窗口来解决。

## 10\. 完整数据流汇总

**上传流程：** 客户端 -\> API 网关（认证） -\> Post 服务 -\> 预签名 S3 URL 客户端 -\> S3（直传） S3 -\> Kafka（post.uploaded） -\> 转码服务 -\> S3（所有变体） 转码服务 -\> Kafka（post.transcoded） -\> 元数据 Worker -\> Posts 数据库 + Redis 缓存 -\> 搜索 Worker -\> Elasticsearch -\> 信息流扇出 Worker -\> Redis 信息流有序集合（普通用户） -\> 名人帖子缓存（高粉丝量用户） 信息流读取流程： 客户端 -\> API 网关 -\> Feed 服务 -\> Redis ZREVRANGE feed:{user\_id}（预计算信息流的帖子 ID） -\> Redis GET 名人帖子（读取时合并） -\> Redis MGET post:1 post:2 ... post:20（填充元数据） -\> CDN（媒体 URL 直接分发） 媒体分发流程： 客户端 -\> CDN 边缘（缓存命中约 90%） -\> 直接返回媒体 客户端 -\> CDN 边缘（缓存未命中约 10%） -\> S3 -\> CDN 缓存 -\> 返回媒体 搜索流程： 客户端 -\> API 网关 -\> 搜索服务 -\> Redis（热门查询缓存） -\> Elasticsearch（缓存未命中时） -\> 帖子元数据缓存（填充结果） 通知流程： 点赞/评论/关注 -\> Kafka -\> 通知服务 -\> 合并事件 -\> 取设备令牌 -\> APNs（iOS）/ FCM（Android） -\> 设备 -\> 通知表（PostgreSQL） -\> 应用内铃铛 互动事件采集： 客户端交互 -\> Kafka -\> 分析 Worker -\> 分析数据库 -\> 机器学习流水线（周期性） -\> Redis（用于信息流排序的个性化信号）

## 11\. 韧性与容错

**CDN + 多分辨率变体**为媒体分发提供了主要韧性。媒体在全球边缘节点上缓存。即使 S3 源站临时不可达，CDN 仍能不中断地继续提供已缓存的媒体。Instagram 内容的幂律分布意味着浏览量最高的帖子几乎总是处于缓存热态。

**Redis 中的预计算信息流**意味着在正常路径下，信息流读取并不依赖 Posts 数据库的健康状况。用户打开 Instagram 时读的是 Redis——即便 Posts 数据库变慢或不可用，已缓存的信息流仍能继续加载。新帖子不再出现，但已有的信息流内容不受影响。

整条流水线上的 **Kafka 解耦**让每个服务都能独立地故障和恢复。信息流扇出 Worker、搜索索引 Worker 和通知服务都以持久化的 offset 从 Kafka 消费，恢复后能追上进度且不丢数据。

针对高写入量路径（分析、信息流事件）的 **Cassandra 复制**确保任何单节点故障都不会导致数据丢失。跨可用区的 3 副本复制因子是标准做法。

Users、Posts、Follows 和 Likes 表的 **PostgreSQL 只读副本**确保关系型这一层在读路径上没有单点故障。所有读流量走副本，写走主节点。

针对不活跃用户信息流的 **Redis 淘汰策略**可防止内存溢出。若干天没有活跃的用户，其信息流会被淘汰，等下次登录时再从 Posts 数据库重建。

服务之间的**熔断器**可防止级联故障。如果 Redis 变慢，Feed 服务会回落到 Posts 数据库，而不是无限期挂起，反之亦然。

## 12\. 技术选型汇总

**API 网关** -\> Kong / AWS API Gateway（认证、限流、路由）

**对象存储** -\> AWS S3（不可变的媒体文件，持久，与 CDN 原生集成）

**CDN** \-\> CloudFront / Akamai（边缘缓存，吸收约 90% 的媒体读负载）

**播放协议** \-\> 视频用 HLS（分片、自适应码率、对 CDN 友好）

**解耦** -\> Apache Kafka（高吞吐事件扇出，持久，可回放）

**搜索引擎** -\> Elasticsearch（全文、模糊匹配、按互动量加权排序）

**帖子 / 用户数据库** \-\> PostgreSQL 分片 + 副本（关系结构，强一致性）

**关注关系图** -\> PostgreSQL + Neo4j / AWS Neptune（关注/取关用 SQL，推荐用图遍历）

**信息流存储** -\> Redis 有序集合（亚毫秒级的排序信息流读取，按用户预计算）

**元数据缓存** -\> Redis MGET（一次往返批量填充帖子元数据）

**分析存储** -\> Cassandra / ClickHouse（高写入量，时序数据，机器学习流水线的输入）

**推送通知** -\> APNs + FCM（iOS 与 Android 的最后一公里投递）

**应用内通知** -\> PostgreSQL + WebSocket（持久化的通知历史 + 实时投递）
